## Арт-студия: настоящий прогресс и панели

Три просьбы пользователя: (1) можно ли упаковать пайплайн в Docker, (2) сделать
нормальный прогресс (внутри кадра полоса стояла), (3) нижнюю панель — вниз
центрального блока, верхний тулбар — информативнее и крупнее.

### Прогресс

Спецификация `docs/specs/art-generation.md` **уже требовала** прогресс шагов по
websocket («ComfyUI отдаёт шаги по websocket, драйвер пересылает их в
`percent`»), а драйвер этого не делал — считал только `[i/N]` по кадрам.
Добавлен `ComfyProgress` в `artgen.py`:

- свой minimal websocket-клиент (рукопожатие, текстовые кадры, pong) — в
  `comfyenv` нет `websocket-client`, а тянуть зависимость ради чтения JSON не
  нужно; против живого ComfyUI 0.38.0 `connected = True`;
- поток отдельный: главный цикл блокирующе читает stdout `shoot.py`, внутри
  кадра тот молчит;
- привязка к кадру по «текущему id» из `[i/N] <id>` — генерация строго
  последовательная, `prompt_id` сопоставлять не нужно (стенд его всё равно не
  печатает целиком);
- `EventWriter.emit` под `threading.Lock` (пишут два потока);
- первый кадр объявляется текущим ДО `Popen`, поэтому пауза загрузки моделей
  (до 410 с) показывает «загрузка модели и подготовка кадра…», а не ноль;
- троттлинг ~3 эмита/с (шаг ~1.3 с, `events.jsonl` — диск).

Проверка без GPU: одноразовый скрипт поднимает подставной websocket-сервер и
убеждается, что `progress` → `item_progress` с `percent`/`text`. Плюс реальный
`/ws` ComfyUI (сервер поднимали и погасили — VRAM не держим).

### Контракт

`item_progress` получил необязательный `text`; добавлено аддитивное событие
`driver_info` (сводка стенда). Версия протокола **не менялась** — правила
`ArtProtocol.cs` это разрешают для обратно совместимых правок.

### Панели

- `bottom-panel` перенесён внутрь `.panel-center`: `x` и ширина совпадают с
  центром (`w=1577`), `body` снова ровно 3 ребёнка.
- Тулбар = две строки (действия + чипы справки) плюс полоса прогресса, видимая
  во время прогона. Дубль прогресса вверху нужен потому, что строка в центре
  живёт на странице каталога и пропадала при открытой очереди ревью.

### Docker — вердикт

На этой машине (Windows + AMD RX 9070 XT, нативный ROCm 7.2.1, подтверждено
`/system_stats`: `pytorch 2.9.1+rocm7.2.1`) Docker — регресс. `--gpus` в Docker
Desktop документирован только для NVIDIA; ROCm в контейнере хочет
`amdgpu-dkms` и `/dev/kfd`+`/dev/dri` из ядра Linux-хоста. ROCDXG завёл ROCm в
**WSL**, но это не `--gpus`. Итог — CPU-инференс, то есть десятки минут на кадр
вместо ~28 с. Плюс «одним файлом» не выйдет: 6 ГБ `comfyenv` + 9.9 ГБ моделей
томом. Docker оправдан только при переезде на Linux. Полный разбор —
`docs/runbooks/portrait-generation.md`, раздел «Упаковка пайплайна».

  без `-u` три строки пришли на 1.53 с (все сразу), с `-u` — 0.02/0.52/1.02 с.

  `Popen`, а `[2/2]` приходил только в конце, поэтому шаги второго кадра и
  прогрева приписывались первому.
- **Прогрев платился каждый прогон:** драйвер не передавал `--no-warmup`, а

  живой `shoot.py` с моделью оставался занимать GPU — следующий прогон вставал

## Арт-студия: почему полоса заполнялась один раз (инкремент 1)

Жалоба: «нижняя заполнилась 1 раз, потом была на 100 %, только верхняя шла
вперёд». Причина оказалась не в интерфейсе, а в очереди — три звена:

1. `item_done` уходит в `generate_frames` **после `proc.wait()`** (проверка
   кадров идёт после отрисовки всех), поэтому задание №1 остаётся `Running`
   весь прогон;
2. `ArtDriverState` делал `Running` только при `Jobs.Running == null` — кадры
   №2..N никогда не становились текущими;
3. окно брало `current = jobs.Running` = первый кадр на `Percent = 99`, а
   `PostSeconds = 4.0` доводил его до 100 % за четыре секунды. Общая полоса
   ползла честно, потому что `SetProgress` пишет по `ev.id`.

**Правило, которое стоит запомнить:** прогресс нельзя выводить из «первого
незакрытого задания». Текущим обязан быть тот, за которым прогресс ПРИШЁЛ, —
то есть по `stand-id`, из события. Порядок событий и порядок заявки не
совпадают.

**Второе:** прогресс теряется там, где процесс молчит, а не там, где медленно.
Пакетная вырезка фона шла через `subprocess.run(capture_output=True)` —
построчные `[i/N]` из `seg.py` копились в буфер и выводились разом ПОСЛЕ
вырезки всей папки raw (100+ файлов). Заменено на `Popen` с построчным
чтением. Схема лечится только на стороне стенда: драйвер не может знать о
чём-то, о чём ему не сообщают.

Три шкалы вместо двух: заявка (среднее вкладов), кадр (сбрасывается в ноль на
каждом кадре), этап (счётчик точно; без счётчика — по времени с потолком 90 %,
иначе «100 %» висит минутами). `DrawnWeight = 90`: кадровая полоса значит
«отрисован», приёмка — за её пределами.

Маркеры стенда — договорённость `shoot.py` ↔ `artgen.py`:
`@@stage <этап> <сделано> <всего> [текст]` и `@@frame <id> drawn`.
Менять молча нельзя — окно перестанет понимать прогресс и вернётся молчание.

EditMode 280/280 Passed. Живой прогон 4+ кадров **не проверен** (окно закрыто).
Отчёт: `docs/reports/2026-10-10-art-studio-progress-stages-report.md`.
