# Stage Planning

## Триггер

Используй, когда:
- начинаешь новую нетривиальную задачу
- требование расплывчатое («сделай чтоб работало»)
- задача затрагивает несколько слоёв
- неясно, какой минимальный инкремент имеет смысл

## Шаг 1. Определить тип работы

```
Новая возможность или большое изменение?
├─ Да → оставаться в plan
└─ Нет → Локальный баг без изменения контракта?
          ├─ Да → можно в build сразу, spec не нужен
          └─ Нет → сомнительно, уточни у пользователя
```

## Шаг 2. Проверить существующий stage

```
docs/stages/
```

- Есть файл под эту задачу? → доработать его, не создавать дубль
- Нет? → создать новый

**Не работать над двумя stages одновременно.** Это прямой запрет из `AGENTS.md`.

## Шаг 3. Сформулировать Goal как ВОЗМОЖНОСТЬ

```
Плохо:  «Реализовать систему инвентаря»        — это слой кода
Плохо:  «Добавить ScriptableObject-ы»          — это инфраструктура
Плохо:  «Сделать сетевой слой»                — это инфраструктура

Отлично: «Игрок может подобрать фонарь, и его свет
          влияет на видимость у всех игроков в сессии»

Отлично: «Два игрока видят движение друг друга,
          и свет каждого виден обоим»
```

**Тест:** можно ли это продемонстрировать в игре? Если нет — цель слишком широкая
или это вообще не цель.

**Тест на слой:** если в формулировке есть слова «система», «слой», «модуль»,
«инфраструктура» — скорее всего это не capability.

## Шаг 4. Определить минимальный инкремент

Вопрос, который стоит задать:

> «Какой минимальный инкремент закрывает главный риск и даёт
> демонстрируемый результат?»

Обычно он **меньше** очевидного. Признаки слишком широкого scope:
- «и ещё», «а также», «плюс»
- перечисление нескольких подсистем
- «полностью», «целиком», «с нуля»

## Шаг 5. Определить Out of scope

**Самая важная часть stage file.** Пишется явно и подробно.

Пример:

```markdown
## Out of scope
- Сеть. Вообще. Ни одного сетевого API.
- Источники света, видимость, фонарики
- Здоровье, урон, смерть
- Враги, ИИ, навигация
- Инвентарь, предметы
- Сохранение
- UI / HUD
- Настройки уровня, освещение сцены, полировка визуала
```

Почему это критично: именно по этому списку на review ты поймаешь
«я заодно ещё и переделал UI».

## Шаг 6. Acceptance criteria

Только **проверяемые** утверждения.

```markdown
❌ «Код работает»
❌ «Хорошо выглядит»
❌ «Играбельно»

✅ «Игрок передвигается по XZ в Play Mode»
✅ «`read_console(action: "get", types: ["error"])` пуст»
✅ «EditMode-тесты проходят»
✅ «Ноль сетевых API вне Assets/Scripts/Net/ — проверяется grep'ом»
✅ «Gameplay-asmdef не ссылается на UnityEditor»
```

Формат: `- [ ] <проверяемое утверждение>`

## Шаг 7. Required tests

| Тип | Что покрывает |
|---|---|
| EditMode | Чистая логика: формулы, состояния, валидаторы, SO |
| PlayMode | MonoBehaviour-жизненный цикл, физика, навигация, UI-поток |
| Grep/статика | Архитектурные границы, `.meta` |

**Обязательно** включить архитектурные проверки, если затронуты слои.

## Шаг 8. Риски и допущения

### Риск

Что может пойти не так и как это смягчить.

| Риск | Митигация |
|---|---|
| Неправильный выбор стека | ADR до кода |
| Слишком ранняя абстракция | Минимальный интерфейс, только нужное сейчас |
| Нестабильная среда | Профилирование до оптимизации |

### Допущение

Что предположил без уточнения. **Обязательно**, иначе оно станет скрытым.

```markdown
## Assumptions
- Будем использовать подход «как в текущей версии» (проверить версию)
- Слой сохраняется липким: панель закрывает ячейку
- Игрок не может взаимодействовать, пока анимация не закончилась
```

## Шаг 9. Work по слоям

Разбей работу по слоям проекта — так видно, не нарушаются ли границы:

```markdown
## Work
### Core
- `IInputReader` в `Assets/Scripts/Core/`
### Gameplay
- `PlayerStamina` — чистая логика
### UI
- Индикатор выносливости (презентация только)
### Editor
- Валидатор архитектурных границ
### Tests
- EditMode: `PlayerStaminaTests`
- PlayMode: переключение ходьба/бег
```

## Шаг 10. Формат вывода плана

```
## Понимание задачи
Своими словами.

## Scope
Что входит.

## Out of scope
Что не входит — явно.

## Acceptance criteria
Проверяемый список.

## Work по слоям
Core / Gameplay / Net / UI / Art / Editor / Tests.

## Риски
Риск → митигация.

## Допущения
Что предположил.

## Верификация
Как проверю: команды + критерии.

## Оценка blast radius
Small / Medium / Large.
```

## Правило

**Не начинай build, пока plan не согласован и out of scope не зафиксирован.**

Вопрос пользователю, если:
- ответ меняет архитектуру слоёв
- ответ меняет сетевой контракт
- есть две разумные архитектуры
- scope расплывчато настолько, что можно сделать три разных варианта

Подробнее: `docs/stages/README.md`, `AGENTS.md → Workflow`
