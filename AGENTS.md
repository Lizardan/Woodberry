# AGENTS.md

## Purpose

**Woodberry** — кооперативный детективный хоррор с видом сверху (референс камеры и читаемости: GTA 2) в мрачной атмосфере.

Игрок — охотник на ведьм, член ордена инквизиции: он берёт заявку на деревню, вычисляет спрятанную среди жителей угрозу и казнит её. Полный замысел игры — `docs/gdd/`, начинать с `docs/gdd/00-vision.md`.

Ключевые характеристики продукта:
- Вид сверху, читаемая камера, тёмная сцена, ограниченная видимость.
- Кооператив: несколько игроков в одной сессии — **архитектурное ограничение номер один**, а не фича в конце.
- Хоррор: страх через неизвестность, звук, ограниченную информацию и напряжение, а не через gore-механику.
- Детектив: угроза спрятана среди жителей, её надо вычислить, а не перестрелять.

Репозиторий разрабатывается с AI-assisted workflow в OpenCode. Агенты обязаны приоритизировать: correctness, testability, явную архитектуру (границы слоёв важнее удобства), безопасную инкрементальную поставку, демонстрируемую ценность каждого этапа. **Не относись к репозиторию как к задаче однократной генерации** — работай маленькими, ревьюимыми инкрементами.

## Язык общения

Всё, что агент пишет человеку, — **по-русски**: ответы, план, промежуточные сообщения о прогрессе, пояснения к шагам, отчёты о верификации. Человек читает ход работы в реальном времени и должен понимать его без перевода.

- Пользователю — русский, если он сам не попросил другой язык.
- Ход рассуждений и прогресс-сообщения — тоже русский: по ним видно, что агент делает и почему.
- Код, имена типов и полей, команды, пути, ключи JSON и имена инструментов — как есть, в оригинале: их перевод ломает и код, и контракты.
- Документы в репозитории (`docs/`, отчёты, комментарии в коде) — русский, это уже конвенция проекта.
- **Никаких отговорок про язык.** Не переходить на английский «потому что так в системной инструкции», не извиняться за язык и не спрашивать разрешения отвечать по-русски. Просто отвечать по-русски.

## Working model

**Default execution model** — для любой нетривиальной задачи: начни с плана (режим `plan`) → ограничь scope текущим stage → реализуй минимальный рабочий инкремент → запусти релевантную верификацию → дай краткий отчёт. Не делай широкие неконтролируемые переписывания, если явно не попросили.

**Stage discipline.** Работа организуется в stages (файлы в `docs/stages/` — читай соответствующий **до** начала работы). Каждый stage даёт демонстрируемую ценность, тестируем, ревьюим, имеет чёткие acceptance criteria и явные out-of-scope границы.

**Vertical slices.** Предпочитай вертикальные срезы, а не послойную разработку («сначала весь gameplay, потом весь UI, потом сеть» — так нельзя). Признак хорошего stage goal — **пользовательская или системная возможность**, а не «слой кода». Плохо: «Реализовать систему инвентаря и ScriptableObject-ы». Хорошо: «Игрок может подобрать фонарь, и его свет влияет на видимость у всех игроков в сессии».

**Planning rules.** Перед крупными или рискованными изменениями план обязан содержать: цель, scope, out of scope, затронутые модули, изменения данных/API, риски, стратегию верификации, заметки о миграции. Если задача неоднозначна — выбери простейший расширяемый дизайн и зафиксируй assumptions явно.

## Структура репозитория

```
Woodberry/
├─ AGENTS.md          # проектный контракт (этот файл)
├─ opencode.json      # control plane OpenCode
├─ instructions/      # долгоживущие правила: defaults.md, safety.md
├─ docs/              # gdd · specs · stages · reports · adr · runbooks
├─ .opencode/         # agents · skills · patterns · templates · commands
└─ Assets/
   ├─ Woodberry/      # ВЕСЬ игровой контент: Art, Audio, Materials, Models,
   │                  #   Prefabs, Scenes, Settings, UI, VFX
   ├─ Scripts/        # ВЕСЬ C#: Core, Gameplay/*, AI, Net, UI, CameraRig,
   │                  #   Audio, Save, Editor
   └─ Tests/          # EditMode · PlayMode
```

Правила структуры:
- **`Assets/Woodberry/` — весь игровой контент.** Не разбрасывай ассеты по корню `Assets/`.
- **`Assets/Scripts/` — весь C# код.** Никаких `.cs` вне этой папки, кроме `Assets/Tests/`.
- **Namespace = `Woodberry.<Слой>[.<Домен>]`.** Пример: `Woodberry.Gameplay.Player`, `Woodberry.Core`, `Woodberry.Net`.
- **Имя файла = имя типа.** Один основной тип на файл. Частные вложенные типы допустимы.
- **`Assets/Scripts/Editor/` — только `#if UNITY_EDITOR`-совместимый код.** Runtime-сборка не ссылается на него.
- **`.meta` файлы коммитятся всегда.** Отсутствующий `.meta` = битая ссылка у всей команды. Никогда не удаляй `.meta` вручную.

## Границы слоёв

Жёсткие границы. Нарушение = architecture drift, ловится на review.

- **`Core`** — composition root, инициализация, game loop, состояния приложения, загрузка сцен. Не содержит геймплейных правил и Unity-рендера/UI.
- **`Gameplay/*`** — игровые правила (движение, здоровье, инвентарь, взаимодействие, состояния врагов). Зависит **только вниз** (`Gameplay → Core`), не вызывает UI и сетевой транспорт напрямую.
- **`Gameplay/Perception`** — обзор и видимость. Правило обзора — **чистая функция** (`VisionCone`, `VisionFanBuilder`, `VisionPolygonBuilder`, `WindowVisionGate`), проверяется EditMode-тестами; рейкасты и отрисовка — в `MonoBehaviour` отдельно. Новый источник реализует `IVisionSource`; препятствие — коллайдер слоя `Occluder`, а не условие в коде. Детали — `docs/adr/0008-visibility-and-darkness.md`.
- **`Net`** — единственное место для транспорта, репликации, спавна, авторитета. Геймплей работает через абстракцию из `Core` — без `if (isNetworked)` в геймплее.
- **`UI`** — презентация: читает состояние, пишет намерения. Не содержит геймплейной логики; один экран = один контроллер/presenter.
- **`AI`** — поведение, навигация, восприятие (`Unity.AI.Navigation`). Не обращается напрямую к полям сущностей — только через сенсорные абстракции.
- **`Editor`** — только редакторные утилиты, весь код под `#if UNITY_EDITOR`; player-сборка его не содержит.

Зависимости: `UI → Gameplay → Core`, `AI → Gameplay`, `Net → Core` (обратно только через интерфейсы), `Editor → всё` (только в редакторе). Запрещено: `Gameplay → UI`, `Gameplay → Net` напрямую, циклы внутри `Gameplay`, `Core → Gameplay`.

## Architecture rules

**Композиция вместо поиска сервисов.** Зависимости передаются явно через конструктор/`Initialize` либо берутся из composition root. `FindObjectOfType` / `GameObject.Find` в геймплейном коде **запрещены** (кроме `Awake` сцены/бутстрапа). Статические синглтоны — только если обоснованы, максимум один на домен, с явным решением в ADR. Единственный разрешённый статический доступ — `Core.ServiceRegistry` (регистрирует **только** composition root, читают объекты сцен один раз) — `docs/adr/0006-scene-architecture-and-service-registry.md`. **`Initialize` остаётся основным путём внедрения**; реестр — только для кросс-сценовых глобальных сервисов.

**События.** Геймплей публикует события через интерфейсы из `Core` (`IGameEvents` и подобные); UI и AI подписываются, но не вызывают геймплей напрямую. Центральный хаб именованных событий хрупок — предпочитай явные подписки или типизированные шины.

**ScriptableObject** — для **дизайн-данных**: параметры врагов, предметов, оружия, настройки уровней. **Не для runtime-состояния** (оно живёт на компонентах/сервисах). Ссылки на SO хранятся в инспекторе, а не ищутся в рантайме. `OnValidate` — для проверки инвариантов дизайн-данных.

**Производительность.** Профилируй до оптимизации, не оптимизируй наугад. Без аллокаций в `Update`/`FixedUpdate` — пулы и переиспользование. `GetComponent` в горячем пути — нарушение, кэшируй в `Awake`. Инстансинг/GPU instancing/объединение мешей — для повторяющихся объектов. Бюджет: 60 FPS на средней машине — `docs/specs/performance-budget.md`.

## Сетевой дизайн (критично — игра кооперативная)

- Определи авторитет для каждого состояния до реализации: клиент **никогда** не является source of truth для игрового состояния.
- Синхронизируй **намерения и результаты**, а не сырые значения каждый кадр.
- Визуальные/косметические вещи (анимации, VFX, звук) — локально, не реплицируй.
- Частота тиков и интерполяция — явные решения, зафиксированные в spec.
- Проверяй, что геймплейный код одинаково работает offline и online; если нет — нарушен слой `Net`.
- `if (isNetworked)`, разбросанный по геймплею — запрещено; один seam в слое `Net`.
- Не доверяй клиенту значения (позиция, урон, цена, инвентарь). Держи серверную симуляцию детерминированной в пределах тика.
- Не реплицируй то, что можно восстановить локально. Не меняй сетевой контракт без обновления spec и ADR.

Детали — `docs/specs/coop-networking.md`, решение стека — `docs/adr/0003-networking-stack.md`.

## Naming conventions

| Тип | Стиль | Пример |
|---|---|---|
| Namespace | `Woodberry.<Layer>.<Domain>` | `Woodberry.Gameplay.Player` |
| Класс (MonoBehaviour) | `PascalCase` | `PlayerController` |
| Скрипт (не MonoBehaviour) | `PascalCase` + `Data`/`Config`/`Service` | `ItemDefinition`, `SaveService` |
| Интерфейс | `I` + `PascalCase` | `IInputReader`, `INetworkService` |
| Метод | `PascalCase` (глагол) | `TryPickUp`, `ApplyDamage` |
| Приватное поле | `_camelCase` | `_health` |
| Публичное поле | не используется; `[SerializeField] private` + property | `_speed` / `Speed` |
| Событие | прошедшее время, `On<Что>` | `OnPlayerDied` |
| Enum | `PascalCase` | `EnemyState` |
| Константа | `PascalCase` | `MaxInventorySlots` |
| Ассет (файл) | `PascalCase` | `PlayerController.prefab` |
| SO ассет | `PascalCase` + `Definition`/`Config` | `Enemy_Zombie.asset` |
| Тест | `<Type>Tests` + метод `X_WhenY_ThenZ` | `HealthTests` |

**Инспектор:** все поля, видимые дизайнеру, — `[SerializeField] private`. Никогда `public` поля в рантайме.

## Code quality

- Простой явный код важнее умных абстракций; без скрытых побочных эффектов и преждевременной генерализации. Следуй существующим конвенциям, если они не явно вредны.
- Один класс — одна ответственность. Если имя требует «And» — раздели.
- Пиши для будущих maintainer'ов, включая агентов. Имена важнее комментариев; комментарий объясняет **почему**, а не **что**.
- Никаких закомментированных кусков кода и unexplained hacks. Нужен workaround — оставь комментарий со ссылкой на issue/ADR.
- Не глотай исключения — логируй с контекстом (`this`, id сущности). Игровые ошибки не крашат редактор: в editor-контексте `Debug.LogError`, в рантайме — свой логгер.
- Публичные методы, меняющие состояние, возвращают `bool`/`Try`-паттерн при возможности неудачи.
- В коде: без `new` в `Update`/`FixedUpdate`/`LateUpdate` без необходимости; `foreach` по `List<T>` без мутации, по массиву — для максимальной скорости; кэшируй `GetComponent` и ссылки в `Awake`/`Start`.

## Unity-specific rules

**Сериализация.** Unity не сериализует: интерфейсы, `Dictionary`, статические поля, делегаты, свойства без backing field, `readonly`. Нужна сложная структура — сделай `[Serializable] struct/class` с полями; нестандарт — `ISerializationCallbackReceiver`.

**MonoBehaviour.** `Awake` → ссылки и кэширование; `Start` → логика инициализации; `OnEnable`/`OnDisable` → подписка/отписка (всегда парно, иначе утечка и краши при domain reload); `OnDestroy` → отписка. Пустой `Update` = удали его. `async void` — только в Unity-подобных coroutine-сценариях (иначе исключения теряются); coroutines — для отложенного действия, не для структурирования кода. `static event` обязательно отписывай.

**Порядок вызовов Unity (не нарушай):** `Awake → OnEnable → Start → FixedUpdate/Update → LateUpdate → OnDisable → OnDestroy`. `Awake` всех объектов сцены выполняется до любого `Start`; на порядок `Start` между объектами не полагайся.

**Сцены и префабы.**
- Три сцены приложения, по одной задаче: `Bootstrap` (сборка и регистрация глобальных сервисов, персистит), `Menu` (точка входа), `Game` (геймплей). Порядок в Build Settings именно такой — `docs/adr/0006-scene-architecture-and-service-registry.md`.
- **Сериализованные ссылки между сценами не сохраняются.** Unity обнуляет их при сохранении сцены, молча. Нужен сервис из `Bootstrap` — бери из `ServiceRegistry`, а не ставь ссылку в инспекторе.
- Переход между сценами — только через `ISceneLoader`. Прямые вызовы `SceneManager` вне `Core` запрещены.
- Префабы — единственный источник правды для повторяющихся объектов; не настраивай дубликаты в сцене. Изменения — `Apply`/`Revert`, ручное редактирование инстансов ломает связь.
- **Никогда не редактируй `.unity`/`.prefab` файлы как текст.** Только Unity Editor или Unity MCP.

**Ввод.** Используй сгенерированный C# класс из `InputSystem_Actions.inputactions`, а не строковые имена экшенов. Не читай ввод в геймплее напрямую — инкапсулируй в `IInputReader`. Разделяй `InputAction` для геймплея и для UI.

**Ассеты и пути.** `Resources.Load` для геймплейных данных запрещён (блокирует сборку, не масштабируется) — Addressables или прямые ссылки; `Resources` допустим только для bootstrap-объекта, который сам загружает остальное. Пути в `Application.dataPath` не хардкодить.

**Ассембли.** Одна сборка на слой, имена совпадают с папками: `Woodberry.Core`, `.Gameplay`, `.AI`, `.Net`, `.UI`, `.CameraRig`, `.Audio`, `.Save`, плюс `Woodberry.Editor` и два тестовых. `Woodberry.Core` не ссылается ни на одну `Woodberry.*` (проверяется компилятором). `Woodberry.Editor.asmdef` обязан иметь `includePlatforms: ["Editor"]`. Ссылки между слоями объявляй явно в `references`, на `autoReferenced` не полагайся. Проверка — меню **Woodberry → Validate Runtime Layers** + EditMode-тесты. Нет сборки — создай до появления кода.

## Testing

- **EditMode** — чистая логика: инвентарь, урон, состояния, формулы, валидаторы, сериализация SO.
- **PlayMode** — MonoBehaviour-жизненный цикл, физика, навигация, взаимодействия, UI-поток.
- **Integration** — контракты между системами: подбор предмета → инвентарь → UI обновился.
- Один тест — одно поведение. Имя: `Method_WhenCondition_ThenExpectedResult`. Не тестируй реализацию — тестируй наблюдаемое поведение. Тест на `[Test]` без ассертов — мусор.
- EditMode-тесты не зависят от сцены. PlayMode-тесты обязаны чистить за собой: `LogAssert.ignoreFailingMessages`, destroy spawn'нутых объектов, снять подписки.
- Не используй `Time.timeScale` для ускорения тестов без явной необходимости.
- **Новая логика без теста = незавершённая задача.** Не говори «готово», если код написан, но не проверен. Если тесты запустить нельзя — **точно скажи почему**. Приоритет: геймплейные правила, сохранение/загрузка, сетевая синхронизация, обработка ошибок.

---

## Верификация

**Канонический источник — `docs/runbooks/unity-automation.md`**: инвентарь инструментов, золотой цикл, что делать нельзя. Ключевое:

- После любого изменения скриптов — `refresh_unity(compile: "request", wait_for_ready: true)`, затем `read_console(types: ["error"])`. При ошибках компиляции не продолжай.
- `run_tests` **асинхронный**: `job_id` — не результат, дождись `get_test_job` со статусом `succeeded`/`failed`. Не запускай тесты при ошибках компиляции (ложный `Passed` на старой сборке). `total: 0` — не ошибка, а отсутствие тестов.
- Инструмента `recompile` **не существует** — есть `refresh_unity`. Имена инструментов не выдумывай, сверяйся с runbook. Editor не запущен — операция делается вручную и помечается `Manual check`.
- Не полагайся на память об Unity API — проверяй через `unity_reflect` / `unity_docs` (версия `6000.6.5f1` свежая).
- Перед «готово» прогони релевантные тесты и приведи **фактический** результат. Не выполнялось — честно пиши `Not verified`.

## Art & asset rules

Полный норматив — **`docs/specs/asset-standards.md`**: имена, ордер папок, текстуры (включая норматив импорта диалогового арта), звук, префабы, материалы, `.meta`, исходники. Здесь только то, чего там нет:

- **Генераторы арта лежат в `.workbuddy-ai/tools/`** (`art_common.py`, `art_character.py`, `art_environment.py`, `art_props.py`). Спрайты процедурные и воспроизводимые: правка — числом в скрипте, а не кистью в PNG. Без скрипта спрайт не воспроизводится и считается потерянным.
- **Персонаж — покадровые спрайты, строго вид сверху.** Не изометрия и не 3/4 — сборка из частей и генерация «на глаз» этот вид не держат (`docs/adr/0009-frame-based-character-sprites.md`).
- **Геометрия маски обзора не может быть дочерней камере**: вершины меша заданы в мировых координатах, и узел-ребёнок увозит их вместе с камерой.

## Workflow

```
Plan → Spec (если меняется контракт) → Build → Verify → Review → Report → Next Stage
```

1. **Plan.** Задача ставится как хорошему инженеру: цель, ограничения, ссылки на существующий код, acceptance criteria. На выходе — план, а не код.
2. **Уточнение.** Уменьшай scope: «какой минимальный инкремент закрывает главный риск и даёт демонстрируемый результат?»
3. **Build.** Ровно согласованный scope, без «улучшений», не включённых в план.
4. **Verify.** Реально запустить команды и честно сообщить статус.
5. **Review.** Отдельный read-only проход через `code-reviewer` (см. ниже).
6. **Report.** Заполнить `docs/reports/<дата>-<stage>-report.md` по шаблону.

**Оставайся в `plan`, если:** архитектура неясна (сначала понять слой), появляются новые контракты (assumptions и acceptance criteria до кода), широкий рефакторинг (риск начать не с того места), затрагивает сеть (сначала authority-модель).

**Specs-first.** Обновляй `docs/specs/`, когда меняется игровой контракт или дизайн-правило, появляется сетевой контракт, меняется схема данных/сохранений или вводится архитектурное ограничение. Локальный баг без изменения intent — spec не нужен.

## Роли

Кого звать под задачу (определения — `.opencode/agents/`; маршрутизация уже настроена в `opencode.json → agent.build.permission.task`, не обходи её):

| Задача | Агент |
|---|---|
| Требования, расплывчатая задача, приоритизация | `system-analyst` |
| Игровая логика, механики, физика | `gameplay-engineer` |
| Сцена, свет, камера, композиция, level flow | `scene-level-designer` |
| Интерфейс, HUD, меню, локализация UI | `ui-engineer` |
| Визуал, материалы, шейдеры, VFX, импорт ассетов | `technical-artist` |
| Сеть, репликация, authority, лаг, хостинг | `gameplay-engineer` → `docs/adr/0003-networking-stack.md` |
| Сборка, билд, CI, релиз, платформы | `unity-tools-engineer` |
| Тесты, баг-репорт, регрессии | `qa-analyst` |
| **Ревью, архитектурный аудит, contract drift** | **`code-reviewer`** (read-only) |

**Разделяй роли build и review.** Агент, который только что написал код, плохо его проверяет. `code-reviewer` — роль **чтения и анализа**, не расширение builder-агента: `edit: deny`, bash — только read-only git (`diff`, `log`, `show`, `status`, `blame`, `ls-files`), навыки `code-review-checklist` и `git-diff-analysis`, `mode: all` (можно `@code-reviewer`), процесс — `docs/specs/code-review-flow.md`. Нашёл проблему — исправляет соответствующий builder-агент **отдельным вызовом, с отдельной ответственностью, никогда сам**. Вызывай после нетривиального этапа, перед merge, при сомнениях в архитектуре. `qa-analyst` **пишет** тесты, `code-reviewer` только читает — это разные роли. У `plan` и `code-reviewer` **нет мутирующих MCP-инструментов**: доступно только чтение Unity (`read_console`, `unity_reflect`, `unity_docs`, состояние редактора), а `execute_code`, `manage_*`, `refresh_unity`, `run_tests` закрыты.

## Anti-patterns

Запрещено в этом репозитории: публичные поля в рантайме вместо `[SerializeField] private`; `FindObjectOfType` в геймплейном коде; бизнес-логика в UI-контроллере; прямые сетевые вызовы из геймплея; ручное редактирование `.unity`/`.prefab` как текста; `Resources.Load` для геймплейных данных; игнорирование `.meta`; «сначала вся система, потом интеграция»; заявление «готово» без запуска проверок; god-классы и «Manager» без ответственности; мёртвый код и закомментированные куски; работа над несколькими stages одновременно без явного указания.

---

## Definition of Done

Stage считается завершённым, только если: scope реализован полностью; acceptance criteria из stage-файла выполнены; добавлены/обновлены релевантные тесты; запущены релевантные проверки (компиляция, тесты); `read_console(types: ["error"])` чист от ошибок компиляции; architecture rules не нарушены; `docs/specs/` обновлены, если менялись контракты; known issues и assumptions явно перечислены; manual QA steps предоставлены; создан stage report в `docs/reports/`; проведён отдельный review-проход.

---

## Формат финального ответа

Для задач на реализацию, в конце ответа: 1) **Summary of changes** — что сделано, 1–3 предложения; 2) **Files/modules affected** — конкретные пути; 3) **Verification performed** — какие команды реально запускались и с каким результатом; 4) **Not verified** — что не удалось проверить и почему; 5) **Known risks / tech debt / assumptions**; 6) **Manual QA steps** — что проверить руками в редакторе; 7) **Recommended next step**. **Не заявляй верификацию, которая не была выполнена.**

---

## Review

Severity-уровни, «что считается Critical» и формат вывода — **источник истины `docs/specs/code-review-flow.md`**. Кратко: 🔴 Critical (нарушение обязательной границы, потеря данных, раскрытый секрет, поломка ассетов у команды) — исправить до merge; 🟠 Major (нарушение правил проекта, contract drift, test gap, риск в hot path) — желательно до merge; 🟡 Minor; 💡 Suggestion. Review ищет: correctness, edge cases, architecture drift, test gaps, contract drift, performance, сетевые проблемы, утечки, избыточную сложность и мёртвый код. Выполняет **отдельный read-only `code-reviewer`**, не автор кода.

## Если не уверен

Прочитай релевантный код → предложи маленький безопасный план → выбери минимальную расширяемую конструкцию → задокументируй assumptions явно → не делай вид, что уверен → спроси, если ответ меняет архитектуру слоёв или сетевой контракт.
