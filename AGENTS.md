# AGENTS.md

## Purpose

**Woodberry** — кооперативный хоррор с видом сверху (референс камеры и читаемости: GTA 2) в мрачной атмосфере.

Ключевые характеристики продукта:
- Вид сверху, читаемая камера, тёмная сцена, ограниченная видимость.
- Кооператив: несколько игроков в одной сессии. Это **архитектурное ограничение номер один**, а не фича в конце.
- Хоррор: страх через неизвестность, звук, ограниченную информацию и напряжение, а не через gore-механику.

Этот репозиторий разрабатывается с AI-assisted workflow в OpenCode.
Агенты, работающие в нём, обязаны приоритизировать:
- correctness
- testability
- явную архитектуру (границы слоёв важнее удобства)
- безопасную инкрементальную поставку
- демонстрируемую ценность каждого этапа

**Не относись к этому репозиторию как к задаче однократной генерации.**
Работай маленькими, ревьюимыми инкрементами.

## Working model

### Default execution model

Для любой нетривиальной задачи:

1. Начни с плана (режим `plan`).
2. Ограничь scope текущим stage.
3. Реализуй минимальный рабочий инкремент.
4. Запусти релевантную верификацию.
5. Дай краткий отчёт по формату ниже.

Не делай широкие неконтролируемые переписывания, если явно не попросили.

### Stage discipline

Работа организуется в stages. Каждый stage:
- даёт демонстрируемую ценность
- тестируем
- ревьюим
- имеет чёткие acceptance criteria
- имеет явные out-of-scope границы

Файлы stages лежат в `docs/stages/`. Читай соответствующий файл **до** начала работы.

### Vertical slices

Предпочитай вертикальные срезы, а не послойную разработку.
Не делай «сначала весь gameplay, потом весь UI, потом сеть».

Признак хорошего stage goal: **пользовательская или системная возможность**, а не «слой кода».
Плохо: «Реализовать систему инвентаря и ScriptableObject-ы».
Хорошо: «Игрок может подобрать фонарь, и его свет влияет на видимость у всех игроков в сессии».

### Правила структуры

- **`Assets/Woodberry/` — весь игровой контент.** Не разбрасывай ассеты по корню `Assets/`.
- **`Assets/Scripts/` — весь C# код.** Никаких `.cs` вне этой папки, кроме `Assets/Tests/`.
- **Namespace = `Woodberry.<Слой>[.<Домен>]`.** Пример: `Woodberry.Gameplay.Player`, `Woodberry.Core`, `Woodberry.Net`.
- **Имя файла = имя типа.** Один основной тип на файл. Частные вложенные типы допустимы.
- **`Assets/Scripts/Editor/` — только `#if UNITY_EDITOR`-совместимый код**, попадает в Editor-сборку. Runtime-сборка не должна ссылаться на него.
- **`.meta` файлы коммитятся всегда.** Отсутствующий `.meta` = битая ссылка у всей команды. Никогда не удаляй `.meta` вручную.

## Layer responsibilities и границы

Это жёсткие границы. Нарушение = architecture drift, который ловится на review.

### Слой `Core`
- Composition root, инициализация игры, сервис-локатор или явная композиция.
- Игровой цикл, состояния приложения, пауза, загрузка сцен.
- **Не содержит** геймплейных правил и не знает про Unity-специфичные системы рендера/UI.

### Слой `Gameplay/*`
- Игровые правила: движение, здоровье, инвентарь, взаимодействие, состояния врагов.
- **Зависит только вниз**: `Gameplay → Core`. Не тянет `Net` в свою логику — вместо этого использует абстракции из `Core`.
- **Не содержит** прямых вызовов UI и сетевого транспорта.

### Слой `Net`
- Единственное место, где живёт сетевой транспорт, репликация, спавн, авторитет.
- Игровой код **никогда** не вызывает сетевые API напрямую. Он работает через абстракцию (интерфейс сервиса), заданную в `Core`.
- Позволяет запускать игру в singleplayer/host/client без `if (isNetworked)` в геймплее.

### Слой `UI`
- Презентация. Читает состояние, пишет намерения.
- **Не содержит геймплейной логики.** Если UI решает игровое правило — это баг слоёв.
- Один экран = один контроллер/ presenter. Бизнес-логика уходит в `Gameplay`.

### Слой `AI`
- Поведение, навигация, восприятие, decision making.
- Потребляет `Unity.AI.Navigation` (`NavMeshSurface`, `NavMeshAgent`).
- **Не обращается напрямую** к полям других сущностей. Восприятие — через сенсорные абстракции.

### Слой `Editor`
- Только редакторные утилиты, кастомные инспекторы, валидаторы, билдеры.
- Весь код под `#if UNITY_EDITOR` либо в папке `Editor`.
- Проверяется правилом: сборка player не должна содержать этот слой.

### Правило зависимостей

```
UI  ─────►  Gameplay  ─────►  Core
                │
AI  ────────────┘

Net ───────────►  Core   (и наоборот только через интерфейсы)

Editor ────────►  всё (но только в редакторе)
```

Запрещено:
- `Gameplay` → `UI` (UI подписывается на геймплей, не наоборот)
- `Gameplay` → `Net` напрямую
- Циклические зависимости между доменами внутри `Gameplay`
- `Core` → `Gameplay` (направление строго вниз)

## Architecture rules

### Композиция вместо поиска сервисов
- Зависимости передаются явно через конструктор или `Initialize`, либо берутся из composition root.
- `FindObjectOfType` / `GameObject.Find` в геймплейном коде — **запрещено**, кроме `Awake` сцены/бутстрапа.
- Статические синглтоны — только если обоснованы, максимум один на домен, и явным решением в ADR.

### События
- Геймплей публикует события через интерфейсы из `Core` (`IGameEvents` и подобные).
- UI и AI подписываются, но не вызывают геймплей напрямую.
- Именованные события в центральном хабе — хрупко. Предпочитай явные подписки или типизированные шины.

### ScriptableObject
- Используется для **дизайн-данных**: параметры врагов, предметов, оружия, настройки уровней.
- **Не используется для runtime-состояния.** Runtime-состояние живёт на компонентах/сервисах.
- Ссылки на SO хранятся в инспекторе, а не ищутся в рантайме.
- Поле `OnValidate` для проверки инвариантов дизайн-данных.

### Сетевой дизайн (критично, т.к. игра кооперативная)
- Определи авторитет для каждого состояния: кто решает. Клиент **никогда** не является source of truth для игрового состояния.
- Синхронизируй **намерения и результаты**, а не сырые значения каждый кадр.
- Визуальные/косметические вещи (анимации, VFX, звук) — локально, не реплицируй.
- Частота тиков и интерполяция — явные решения, зафиксированные в spec.
- Проверяй, что геймплейный код одинаково работает в offline и online: если нет — нарушен слой `Net`.
- Подробности: `docs/specs/coop-networking.md`, решение стека — `docs/adr/0003-networking-stack.md`.

### Производительность
- Профилируй до оптимизации. Не оптимизируй наугад.
- Избегай аллокаций в `Update`/`FixedUpdate` — используй пулы и переиспользование.
- `GetComponent` в горячем пути — нарушение. Кэшируй в `Awake`.
- Инстансинг, GPU instancing, объединение мешей — для повторяющихся объектов.
- Целевой бюджет: 60 FPS на средней машине; профильный слой в `docs/specs/performance-budget.md`.

## Naming conventions

| Тип | Стиль | Пример |
|---|---|---|
| Namespace | `Woodberry.<Layer>.<Domain>` | `Woodberry.Gameplay.Player` |
| Класс (MonoBehaviour) | `PascalCase` | `PlayerController` |
| Скрипт (не MonoBehaviour) | `PascalCase` + `Data`/`Config`/`Service` | `ItemDefinition`, `SaveService` |
| Интерфейс | `I` + `PascalCase` | `IInputReader`, `INetworkService` |
| Метод | `PascalCase` (глагол) | `TryPickUp`, `ApplyDamage` |
| Приватное поле | `_camelCase` | `_health` |
| Публичное поле | не используется; `[SerializeField] private` + property | `_speed` / `Speed` |
| Событие | прошедшее время, `On<Что>` | `OnPlayerDied` |
| Enum | `PascalCase` | `EnemyState` |
| Константа | `PascalCase` | `MaxInventorySlots` |
| Ассет (файл) | `PascalCase` | `PlayerController.prefab` |
| SO ассет | `PascalCase` + `Definition`/`Config` | `Enemy_Zombie.asset` |
| Тест | `<Type>Tests` + метод `X_WhenY_ThenZ` | `HealthTests` |

**Инспектор:** все поля, видимые дизайнеру, — `[SerializeField] private`. Никогда `public` поля в рантайме.

## Code quality rules

### Общее
- Простой явный код важнее умных абстракций.
- Избегай скрытых побочных эффектов.
- Не вводи преждевременную генерализацию.
- Следуй существующим конвенциям, если они не явно вредны.
- Один класс — одна ответственность. Если имя класса требует «And» — раздели.

### Читаемость
- Пиши для будущих Maintainer'ов, включая агентов.
- Имена важнее комментариев. Комментарий объясняет **почему**, а не **что**.
- Никаких закомментирован-out кусков кода. Удали или объясни.
- Никаких unexplained hacks. Если нужен workaround — оставь комментарий со ссылкой на issue/ADR.

### Производительность в коде
- Никаких `new` в `Update`, `FixedUpdate`, `LateUpdate` без необходимости.
- `foreach` по `List<T>` без мутации; по массиву для максимальной скорости.
- Кэшируй `GetComponent` и ссылки в `Awake`/`Start`.

### Обработка ошибок
- Не глотай исключения. Логируй с контекстом (`this`, id сущности).
- Игровые ошибки не крашат редактор: в editor-контексте можно использовать `Debug.LogError`, но в рантайме используй свой логгер.
- Публичные методы, меняющие состояние, возвращают `bool`/`Try`-паттерн при возможности неудачи.

## Unity-specific rules

### Сериализация
- Unity не сериализует: интерфейсы, `Dictionary`, статические поля, делегаты, свойства без backing field, `readonly` поля.
- Если нужно сериализовать сложную структуру — сделай `[Serializable] struct/class` с полями.
- `ISerializationCallbackReceiver` для нестандартной сериализации.

### MonoBehaviour
- Не делай тяжёлую работу в `Awake`/`Start` без причины.
- `Awake` → ссылки и кэширование. `Start` → логика инициализации.
- `OnEnable`/`OnDisable` → подписка/отписка. Всегда парно, иначе будет утечка и краши при domain reload.
- `OnDestroy` → отписка, если подписка не была в паре с `OnDisable`.
- `Update` пустой = удали его, Unity вызывает его каждый кадр.
- Никогда не используй `async void` кроме Unity-подобных coroutine-сценариев — исключения потеряются.
- Coroutines для отложенного действия, не для структурирования кода.
- Статические события (`static event`) обязательно отписывай, иначе утечка через domain reload.

### Порядок вызовов Unity (не нарушай)
```
Awake → OnEnable → Start → FixedUpdate/Update → LateUpdate → OnDisable → OnDestroy
```
`Awake` всех объектов сцены выполняется до любого `Start`. Не полагайся на порядок `Start` между объектами.

### Сцены и префабы
- Префабы — единственный источник правды для повторяющихся объектов. Не настраивай дубликаты в сцене.
- Префабы не должны содержать логики, зависящей от единственного экземпляра.
- Изменения в префабе — `Apply`/`Revert`, ручное редактирование инстансов ломает связь.
- **Никогда не редактируй `.unity`/`.prefab` файлы как текст.** Только через Unity Editor или Unity MCP. Ручной YAML-редактит Unity-ассетов почти всегда приводит к поломке.

### Ввод
- Используй сгенерированный C# класс из `InputSystem_Actions.inputactions`, а не строковые имены экшенов.
- Не читай ввод в геймплее напрямую — инкапсулируй в `IInputReader`.
- Разделяй `InputAction` для геймплея и для UI.

### Ассеты и пути
- Никогда не используй `Resources.Load` для геймплейных данных. Это блокирует сборку и не масштабируется. Используй Addressables или прямые ссылки.
- `Resources` допустим только для bootstrap-объекта, который сам загружает остальное.
- Пути в `Application.dataPath` не хардкодить.

### Ассембли
- Игровой код должен лежать в asmdef. Это делает границы слоёв компиляемым контрактом, а не соглашением.
- **Одна сборка на слой.** Имена совпадают с папками: `Woodberry.Core`, `Woodberry.Gameplay`,
  `Woodberry.AI`, `Woodberry.Net`, `Woodberry.UI`, `Woodberry.CameraRig`, `Woodberry.Audio`,
  `Woodberry.Save`, плюс `Woodberry.Editor` и два тестовых.
- `Woodberry.Core` не ссылается ни на одну сборку `Woodberry.*` — это проверяется компилятором.
- `Woodberry.Editor.asmdef` обязан иметь `includePlatforms: ["Editor"]`.
- Ссылки между слоями объявляй явно в `references` asmdef. На автоссылку (`autoReferenced`) не полагайся: она не даёт нужного направления зависимостей.
- Проверка: **Woodberry → Validate Runtime Layers** в меню, плюс EditMode-тесты.
- Если сборки нет — создай её до того, как в папке появится код.

## Testing rules

Тесты обязательны для значимых изменений.

### Что тестировать
- **EditMode** — чистая логика: инвентарь, урон, состояния, формулы, валидаторы, сериализация SO.
- **PlayMode** — MonoBehaviour-жизненный цикл, физика, навигация, взаимодействия, UI-поток.
- **Integration** — контракты между системами: подбор предмета → инвентарь → UI обновился.

### Правила
- Не пиши тест, который проверяет сам себя. Тест на `[Test]` без ассертов — мусор.
- Один тест — одно поведение. Имя: `Method_WhenCondition_ThenExpectedResult`.
- Не тестируй реализацию — тестируй наблюдаемое поведение.
- Не используй `Time.timeScale` для ускорения тестов без явной необходимости.
- EditMode-тесты не должны зависеть от сцены.
- PlayMode-тесты обязаны чистить за собой: `LogAssert.ignoreFailingMessages`, destroy spawn'нутые объекты, снимать подписки.

### Ответственность агентов
- Новая логика без теста = незавершённая задача.
- Не говори «готово», если код написан, но не проверен.
- Если тесты запустить нельзя — **точно скажи почему**.
- Приоритет тестов: геймплейные правила, сохранение/загрузка, сетевая синхронизация, обработка ошибок.

## Verification commands

Запускай минимально достаточный набор проверок для текущего scope.

### Статус автоматизации

**Unity MCP установлен и работает.** Пакет `com.coplaydev.unity-mcp`,
сервер `mcpforunityserver==10.2.0`, инстанс `Woodberry@93447b6f` (порт `6400`).

Секция `mcp` есть в `opencode.json`, значит конфигурация версионируется вместе
с репозиторием. Инструментов 47; имена сверены с фактическим `tools/list` и
проверены вызовом. Полный инвентарь с разделением «проверено / не проверено» —
`docs/runbooks/unity-automation.md`.

### Золотой цикл

Вызовы каноническими именами (клиент добавляет префикс `unityMCP_`):

```
1. read_console(action: "clear")
2. refresh_unity(mode: "if_dirty", compile: "request", wait_for_ready: true)
3. read_console(action: "get", types: ["error", "warning"], count: 50)
4. если ошибок нет -> run_tests(mode: "EditMode") -> get_test_job(job_id: ..., wait_timeout: 60)
5. записать в отчёт: что проверено, что нет
```

Другие частые вызовы:

```
# Состояние редактора (ресурс, а не инструмент)
mcpforunity://editor/state  ->  data.advice.ready_for_tools, data.compilation.is_compiling
mcpforunity://instances     ->  список Editor'ов

# Проверка Unity API — вместо памяти
unity_reflect(action: "get_member", class_name: "UnityEngine.AI.NavMeshAgent", member_name: "speed")
unity_docs(action: "get_doc", class_name: "CharacterController")

# Иерархия сцены — всегда с page_size
manage_scene(action: "get_hierarchy", page_size: 50, max_depth: 2)

# Сборка
manage_build(action: "scenes")
manage_editor(action: "play") / manage_editor(action: "stop")
```

**Правила:**
- После любого изменения скриптов — `refresh_unity` с `compile: "request"`, затем
  `read_console` за ошибками. Не продолжай при ошибках компиляции.
- `run_tests` **асинхронный**. Ответ с `job_id` не результат: дождись
  `get_test_job` со статусом `succeeded`/`failed`.
- Не запускай тесты при ошибках компиляции — Unity вернёт ложный `Passed`
  на старой сборке.
- `total: 0` в результате тестов — не ошибка, а отсутствие тестов.
- Перед тем как заявить «готово», прогони релевантные тесты и приведи **фактический** результат.
- Если проверка не выполнялась — честно пиши это в отчёте как `Not verified`.
- Не приписывай агенту инструменты, которых у него нет. Сверяйся с
  `docs/runbooks/unity-automation.md`; инструмента `recompile` **не существует** —
  есть `refresh_unity`. Если Editor не запущен, операция делается вручную и
  отмечается как `Manual check`.
- Не доверяй памяти о Unity API: проверяй через `unity_reflect` / `unity_docs`.
  Unity `6000.6.3f1` свежая, память устаревает.

## Art & asset rules

- Ордер ассетов: `Assets/Woodberry/<Category>/<Subcategory>/`.
- Имена ассетов — `PascalCase`, без пробелов. Имена, которые Unity сам генерирует (`New GameObject`), переименовывай сразу.
- Общие ассеты (материалы, UI-спрайты, SFX) — в общих папках, не копируй их между сценами.
- Спрайты: настройки импорта задавай осмысленно (PPU, compression, filter mode, mipmaps). Для пиксель-арта — Point filter, без mipmaps.
- Звук: разделяй Music / SFX / Ambience / UI. Для 3D-звука — spatial blend осмысленно.
- Не коммить `.psd`, `.blend`, `.fbx`-исходники, если их можно заменить экспортированной версией (или хотя бы держи в отдельной папке с понятным правилом).

## Multiplayer-specific Do/Don't

Игра кооперативная, поэтому:

**Do:**
- Определять authority для каждого игрового состояния до реализации.
- Отделять intent (хочу подобрать) от результата (подобрал).
- Держать серверную симуляцию детерминированной в пределах тика.
- Писать спеку до реализации: `docs/specs/coop-networking.md`.
- Тестировать, что поведение одинаково в host и client.

**Don't:**
- Не доверять клиенту значения (позиция, урон, цена, инвентарь).
- Не делать `if (isNetworked)` разбросанным по геймплею. Один seam в слое `Net`.
- Не реплицировать то, что можно восстановить локально.
- Не изменять сетевой контракт без обновления spec и ADR.

## Workflow

### Цикл работы

```
Plan → Spec (если меняется контракт) → Build → Verify → Review → Report → Next Stage
```

1. **Plan.** Задача ставится как хорошему инженеру: цель, ограничения, ссылки на существующий код, acceptance criteria. На выходе — план, а не код.
2. **Уточнение.** Уменьшай scope: «какой минимальный инкремент закрывает главный риск и даёт демонстрируемый результат?»
3. **Build.** Ровно согласованный scope. Без «улучшений», не включённых в план.
4. **Verify.** Реально запустить команды и честно сообщить статус.
5. **Review.** Отдельный read-only проход через `code-reviewer`: correctness, edge cases, architecture drift, test gaps, contract drift. Процесс — `docs/specs/code-review-flow.md`.
6. **Report.** Заполнить `docs/reports/<дата>-<stage>-report.md` по шаблону.

### Когда оставаться в `plan`

| Ситуация | Почему не сразу в build |
|---|---|
| Архитектура неясна | Сначала понять, в каком слое живёт изменение |
| Новые контракты | Сформировать assumptions и acceptance criteria до кода |
| Широкий рефакторинг | Риск начать не с того места |
| Затрагивает сеть | Сначала authority-модель, потом реализация |

### Specs-first

Обновляй `docs/specs/`, когда:
- меняется игровой контракт или дизайн-правило
- появляется новый сетевой контракт
- меняется схема данных/сохранений
- вводится архитектурное ограничение

Не нужен spec, если это локальный баг без изменения intent.

## Role routing

Кого звать под какую задачу. Подробные определения — в `.opencode/agents/`.

| Задача | Агент |
|---|---|
| Изменить требования, расплывчатая задача, приоритизация | `system-analyst` |
| Игровая логика, геймплей, механики, физика | `gameplay-engineer` |
| Сцена, свет, камера, композиция, level flow | `scene-level-designer` |
| Интерфейс, HUD, меню, локализация UI | `ui-engineer` |
| Визуал, материалы, шейдеры, VFX, импорт ассетов | `technical-artist` |
| Сеть, репликация, authority, лаг, хостинг | `gameplay-engineer` → `docs/adr/0003-networking-stack.md` |
| Сборка, билд, CI, релиз, платформы | `unity-tools-engineer` |
| Тесты, баг-репорт, регрессии | `qa-analyst` |
| **Ревью изменений, архитектурный аудит, contract drift** | **`code-reviewer`** (read-only) |

Маршрутизация через `opencode.json` → `agent.build.permission.task` уже настроена. Не обходи её.

### Разделение ролей: build и review

**Агент, который только что написал код, плохо его проверяет.**
Разделяй роли во времени, а не одновременно:

```
build-агент реализует → Stage Report → code-reviewer делает независимый review
```

`code-reviewer` — **роль чтения и анализа**, а не расширение builder-агента:

| Свойство | Значение |
|---|---|
| Права | `edit: deny` — не может изменить файл, даже случайно |
| Bash | только read-only git: `diff`, `log`, `show`, `status`, `blame`, `ls-files` |
| Навыки | `code-review-checklist`, `git-diff-analysis` |
| Режим | `mode: all` — можно вызвать напрямую через `@code-reviewer` |
| Спецификация процесса | `docs/specs/code-review-flow.md` |

Если `code-reviewer` нашёл проблему — исправляет её соответствующий builder-агент,
**отдельным вызовом, с отдельной ответственностью**. Никогда сам.

Вызывай `code-reviewer`:
- после любого нетривиального этапа
- перед merge
- когда сомневаешься, что изменение вписывается в архитектуру

Вызывай `qa-analyst`:
- когда нужно **написать** тесты
- когда нужен регрессионный прогон
- когда нужен баг-репорт

Это разные роли. `qa-analyst` пишет тесты, `code-reviewer` только читает.

## Anti-patterns

Запрещено в этом репозитории:

- Публичные поля в рантайме вместо `[SerializeField] private`
- `FindObjectOfType` в геймплейном коде
- Бизнес-логика в UI-контроллере
- Прямые сетевые вызовы из геймплея
- Ручное редактирование `.unity`/`.prefab` как текста
- `Resources.Load` для геймплейных данных
- Игнорирование `.meta` файлов
- «Сначала вся система, потом интеграция»
- Заявление «готово» без запуска проверок
- God-классы, «Manager» без ответственности
- Мёртвый код и закомментированные куски
- Работа над несколькими stages одновременно без явного указания

## Definition of Done

Stage считается завершённым, только если:

- [ ] scope реализован полностью
- [ ] acceptance criteria из stage file выполнены
- [ ] добавлены или обновлены релевантные тесты
- [ ] запущены релевантные проверки (компиляция, тесты)
- [ ] `read_console(action: "get", types: ["error"])` чист от ошибок компиляции
- [ ] architecture rules не нарушены
- [ ] `docs/specs/` обновлены, если менялись контракты
- [ ] known issues явно перечислены
- [ ] assumptions явно перечислены
- [ ] manual QA steps предоставлены
- [ ] создан stage report в `docs/reports/`
- [ ] проведён отдельный review-проход

## Expected final response format

Для задач на реализацию, в конце ответа:

1. **Summary of changes** — что сделано, 1–3 предложения
2. **Files/modules affected** — конкретные пути
3. **Verification performed** — какие команды реально запускались и с каким результатом
4. **Not verified** — что не удалось проверить и почему
5. **Known risks / tech debt / assumptions** — честно
6. **Manual QA steps** — что проверить руками в редакторе
7. **Recommended next step** — логичный следующий шаг

**Не заявляй верификацию, которая не была выполнена.**

## Review expectations

Review-проход ищет:

- correctness (правильность логики)
- edge cases (пустые данные, null, гонки, отсутствие ресурсов)
- architecture drift (смешение слоёв, нарушения границ)
- test gaps (логика без тестов, happy path без негативных)
- contract drift (spec разошёлся с кодом)
- performance (аллокации в hot path, `GetComponent` в цикле)
- сетевые проблемы (доверие клиенту, рассинхрон)
- утечки (неотписанные подписки, `static event`)
- избыточная сложность и мёртвый код

Severity-уровни и формат вывода заданы в `docs/specs/code-review-flow.md` —
это источник истины. Кратко:

| Уровень | Значение | Действие |
|---|---|---|
| 🔴 Critical | Нарушение обязательной архитектурной границы, потеря данных, раскрытый секрет, поломка ассетов у команды | Обязательно исправить до merge |
| 🟠 Major | Нарушение правил проекта, contract drift, test gap, риск в hot path | Желательно исправить до merge |
| 🟡 Minor | Naming, комментарии, небольшие пробелы | Исправить или зафиксировать как компромисс |
| 💡 Suggestion | Рефакторинг, улучшение, идея на будущее | Опционально |

Что считается **Critical** в этом проекте — перечислено явно в
`docs/specs/code-review-flow.md`. Коротко: сетевой API вне `Net/`,
`if (isNetworked)` в геймплее, `Gameplay` → `UI`, `Core` → `Gameplay`,
runtime-код с `UnityEditor`, ручной YAML-редакт Unity-ассетов,
ассет без `.meta`, дубль контроллера игрока, секрет в коде.

Ревью выполняет **отдельный read-only агент `code-reviewer`**, а не тот же агент,
что писал код. Процесс — в `docs/specs/code-review-flow.md`.

## If unsure

- Сначала прочитай релевантный код.
- Предложи маленький безопасный план.
- Выбери минимальную расширяемую конструкцию.
- Задокументируй assumptions явно.
- Не делай вид, что уверен, если не уверен.
- Спроси, если ответ меняет архитектуру слоёв или сетевой контракт.
