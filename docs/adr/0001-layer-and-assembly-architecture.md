# ADR 0001 — Layer and Assembly Architecture

## Status

Accepted

## Date

2026-09-30

## Context

Игра — кооперативный top-down хоррор. На старте проекта 0 скриптов, 0 asmdef, вся
будущая сложность — впереди. Нужно выбрать структуру, которая:

- не даст UI решать игровые правила
- не даст геймплею знать про сеть
- не даст `Core` зависеть от конкретных подсистем
- позволит тестировать чистую логику без сцены
- сделает границы **проверяемыми компилятором**, а не соглашением в чате

Соглашение «так не делаем» в документе не работает: оно забывается через два месяца.
Assembly definition файл превращает правило в ошибку компиляции.

## Decision

### Слои

```
UI  ─────►  Gameplay  ─────►  Core
                ▲
AI  ────────────┘

Net ───────────►  Core   (обратно — только через интерфейсы)

Editor ────────►  всё (только в редакторе)
```

### Ответственность слоёв

| Слой | Путь | Ответственность |
|---|---|---|
| `Core` | `Assets/Scripts/Core/` | Composition root, игровой цикл, абстракции (`INetworkService`, `IInputReader`) |
| `Gameplay` | `Assets/Scripts/Gameplay/` | Игровые правила: движение, здоровье, инвентарь, взаимодействие, состояния врагов |
| `AI` | `Assets/Scripts/AI/` | Поведение, навигация, восприятие |
| `Net` | `Assets/Scripts/Net/` | Сетевой транспорт, репликация, спавн, авторитет. Единственное место с сетевым кодом |
| `UI` | `Assets/Scripts/UI/` | Презентация. Читает состояние, пишет намерения |
| `CameraRig` | `Assets/Scripts/CameraRig/` | Камера и её поведение |
| `Audio` | `Assets/Scripts/Audio/` | Звуковой слой |
| `Save` | `Assets/Scripts/Save/` | Сериализация и хранение |
| `Editor` | `Assets/Scripts/Editor/` | Только редакторные утилиты |

### Asmdef-файлы

| Assembly | Тип | Ссылки |
|---|---|---|
| `Woodberry.Core` | Runtime | — |
| `Woodberry.Runtime` | Runtime | `Woodberry.Core` |
| `Woodberry.Editor` | Editor | `Woodberry.Core`, `Woodberry.Runtime` |
| `Woodberry.Tests.EditMode` | Editor | `Woodberry.Core`, `Woodberry.Runtime` |
| `Woodberry.Tests.PlayMode` | Runtime | `Woodberry.Core`, `Woodberry.Runtime` |

На старте `Core` и остальной runtime объединены в `Woodberry.Runtime` — это сознательно:
дробить сборки под каждый домен до появления реального кода создаёт церемонию без пользы.
`Core` отделяется, как только в нём появится что-то, что не должно видеть геймплей.

Почему один `Woodberry.Runtime`, а не `Woodberry.Gameplay` / `Woodberry.AI` / `Woodberry.UI`:

Unity не различает папки на уровне сборки без asmdef в каждой. Создание 8 сборок на пустом
проекте даёт 8 файлов, 0 проверяемых правил и кучу хрупких `references`.
Правило «UI не решает игровые правила» проверяется **review-ом**, а не компилятором, —
и это приемлемо на старте. Когда появится реальный объём — разделим, и это будет
осознанное изменение, а не конвенция.

### Направление зависимостей — строго вниз

`Core` **не знает** про `Gameplay`. Если `Core` ссылается на геймплей — нарушение.

Исключение: composition root. Он существует, чтобы собирать зависимости вниз вверх,
и находится в `Core`, но ссылается на конкретные реализации через интерфейсы
и подключается в сцене как единственная точка входа.

### Namespace

`Woodberry.<Слой>[.<Домен>]`

```
Woodberry.Core
Woodberry.Gameplay.Player
Woodberry.Gameplay.Enemies
Woodberry.Gameplay.Items
Woodberry.Net
Woodberry.UI
```

### Имя файла = имя типа

Один основной тип на файл. Частные вложенные типы допустимы. Это делает навигацию
и `git log --follow` предсказуемыми.

## Consequences

### Positive

- Нарушение границ ловится компилятором, а не на ревью
- Чистую логику можно тестировать в EditMode без сцены
- `Editor`-слой не попадает в player-сборку по построению
- Сетевой код физически отделён — его видно целиком в одной папке
- Новый агент может ориентироваться в структуре, не задавая вопросов

### Negative

- Два уровня вложенности asmdef → больше файлов в репозитории
- При росте проекта понадобится разбить `Woodberry.Runtime` на доменные сборки
- `references` надо поддерживать вручную при добавлении новых сборок
- Физически невозможно создать `Woodberry.Core`-зависимость от геймплея — это плюс,
  но иногда хочется, и придётся правильно рефакторить, а не быстро

## Alternatives considered

### Ассембли на каждый слой сразу (8+ файлов)

Отклонено. На пустом проекте это церемония без проверяемых правил. Разделим, когда
появится реальный объём кода.

### Один `Woodberry.Runtime` без `Core`

Отклонено. `Core` — это именно то, что позволяет определить «вниз», не создавая
иерархию. Без него правило зависимостей невыразимо.

### Без asmdef вообще (Assembly-CSharp)

Отклонено. Тогда границы слоёв — исключительно соглашение, что для AI-assisted
разработки недостаточно: агент не проверит правило компилятором.

### asmdef на каждый домен геймплея

Отложено. Рассмотреть после Stage 03, когда появится реальный объём и станет видно,
какие домены действительно независимы.

## Revisit when

- Появится 500+ строк кода в `Woodberry.Runtime`
- `Core` начнёт «протекать» в `Gameplay`-зависимости (нужна отдельная сборка)
- Stage 03 покажет, что `Net` требует изоляции от `Core`
