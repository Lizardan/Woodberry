# ADR 0006 — Scene Architecture and Global Service Registry

## Status

Accepted

## Date

2026-09-30

## Context

Приложение выросло из одной сцены в три: `Bootstrap` (сборка сервисов),
`Menu` (вход в игру) и `Game` (геймплей). Одновременно выяснилось, что
Composition root не может раздать сервисы объектам других сцен привычным
способом.

### Почему привычные способы не работают

**Сериализованные ссылки между сценами Unity не сохраняет.**
Проверено экспериментом: объект сцены A, на который ссылается поле объекта
сцены B, при сохранении B превращается в `{fileID: 0}`. Ссылка теряется уже
на этапе сохранения — не при загрузке. Воспроизводится при живом объекте
и загруженной сцене-доноре.

Значит схема Stage 00 (`PlayerController._bootstrap → GameBootstrap`) работала
только пока bootstrap и игрок лежали в одной сцене. При разнесении игрок тихо
остался бы без ввода: ошибки компиляции нет, в консоли чисто, в редакторе всё
выглядит исправно.

**`FindObjectOfType` в геймплее запрещён** правилами проекта, и правильно:
он делает зависимости невидимыми.

**Статический синглтон отвергнут** в ADR 0005 как скрытая зависимость.

## Decision

### Три сцены

| Сцена | Индекс | Назначение |
|---|---|---|
| `Bootstrap.unity` | 0 | Создаёт и регистрирует глобальные сервисы, `DontDestroyOnLoad`, уводит в `Menu` |
| `Menu.unity` | 1 | Главное меню, единственная точка входа в игру |
| `Game.unity` | 2 | Геймплей: игрок, камера, уровень |

Имена файлов без префикса `Woodberry_` — папка `Assets/Woodberry/Scenes/`
уже задаёт контекст.

Переходы идут через `LoadSceneMode.Single`: в каждый момент активна ровно
одна сцена. `Menu` не должна висеть под игрой — иначе по ней можно ходить.
`Bootstrap`-объект при этом выживает, потому что переехал в `DontDestroyOnLoad`.

### `ServiceRegistry` — единственный канал к глобальным сервисам

```csharp
namespace Woodberry.Core
{
    public static class ServiceRegistry
    {
        public static void Register<T>(T service) where T : class;
        public static bool TryGet<T>(out T service) where T : class;
        public static void Unregister<T>() where T : class;
        public static void Clear();
    }
}
```

Регистрирует **только** composition root. Читают объекты сцен, один раз,
обычно в `Start`. Реестр сбрасывается на
`RuntimeInitializeLoadType.SubsystemRegistration`, иначе состояние статического
словаря протекало бы между прогонами Play Mode в редакторе.

Сейчас в реестре: `IInputReader` и `ISceneLoader`. Сетевая сессия, сейв и
загрузчики уровней добавятся сюда же, когда появятся.

### `ISceneLoader` — уход в другую сцену как намерение

UI не знает про `SceneManager`. Кнопка Play пишет намерение
`ISceneLoader.Load(SceneId.Game)`. Единственная реализация
`UnitySceneLoader` — единственный класс в проекте, знающий про загрузку сцен.

`SceneId` и `ScenePaths` — единственное место, где сцены сопоставлены с файлами.

### Стартовая инициализация и экран загрузки

`Bootstrap` не уходит в меню сразу. Он выполняет пайплайн
инициализации и переходит **только** после того, как всё готово:
переход на недособранных зависимостях отложил бы отказ и сделал его
невнятным.

- `IStartupStep` — шаг. `IEnumerator`, потому что реальные шаги асинхронны.
- `StartupRunner` — выполняет шаги последовательно.
- `IStartupProgress` — сервис, а не поле компонента: экран загрузки живёт в
  сцене, которая выгружается первой, а прогресс нужен дольше.
- `StartupLoadingView` в слое `UI` — **только** презентация. Когда переходить,
  решает Core. Иначе презентация решала бы вопрос порядка инициализации.

Сейчас реальный шаг один, `RegisterServicesStep`. Как только появятся загрузка
ассетов и сессия, шаги добавляются в `GameBootstrap.BuildSteps()`; экран
начнёт показывать реальный прогресс без правок.

Пока шаг один и он быстрый, полоса проходит незаметно. Это сознательно:
искусственные задержки ради видимой полосы врали бы игроку.

### Что остаётся от ADR 0005

Без изменений: `IInputReader` остаётся единственной точкой доступа к вводу,
в геймплее нет строковых имён экшенов, `Enable`/`Disable` парные,
`NetworkedInputReader` для remote-игроков по-прежнему возвращает нули.

## Consequences

### Positive

- Глобальный сервис доступен из любой сцены без `FindObjectOfType`
  и без неработающей сериализованной ссылки.
- `GameBootstrap` стал настоящим composition root: сцена `Bootstrap` нужна
  только для сборки, её объекты уезжают в `DontDestroyOnLoad`.
- Меню — отдельное состояние приложения. Куда войти, когда играть и что
  грузить — решается в одном месте, а не размазано по геймплею.
- Ошибка «сервис не зарегистрирован» диагностируется внятно, а не приводит
  к молчаливому отказу.
- Реестр покрыт EditMode-тестами, переходы — PlayMode-тестами.

### Negative

- **Реестр — глобальное мутабельное состояние.** Это цена, а не бесплатно.
  Смягчения: единственный писатель (composition root), чтение один раз,
  сброс на `SubsystemRegistration`, тесты на утечку состояния.
- **Реестр маскирует зависимости.** Код выглядит автономным, а сервис
  приходит откуда-то. Поэтому `Initialize` остаётся основным путём подстановки,
  а реестр — только для кросс-сценовых глобальных сервисов.
- Создание `GameBootstrap` в произвольной сцене уводит приложение в меню.
  Это ловушка для тестов: тест, создавший bootstrap ради ввода, выгружал
  сцену из-под себя. Зафиксировано в `SceneFlowTests` и учтено в
  `PlayerControllerTests`.
- `DontDestroyOnLoad` — единственный известный способ сохранения состояния
  между сценами, и он не сериализуется: сервисы, созданные в коде, при
  перезагрузке домена не восстанавливаются. Отсюда требование собирать
  всё в `Awake`, а не восстанавливать поля.

## Alternatives considered

### Ссылка в инспекторе на объект другой сцены

Отклонено: **не работает.** Проверено экспериментом, ссылка обнуляется
при сохранении.

### `FindObjectOfType` в composition root

Отклонено: ломает правило проекта и делает состав сервисов невидимым.

### Статический `InputReader.Instance`

Отклонено в ADR 0005, позиция сохранена: сервисов станет много, а точка
связности — одна.

### Ввод живёт в сцене `Game`, рядом с игроком

Отклонено как основной вариант: формально чище, но противоречит модели
«bootstrap собирает всё, что нужно». Ввод — сервис сессии, а не свойство
объекта сцены. Практический минус: по этому пути `Menu` всё равно
понадобился бы собственный ввод для навигации, то есть два разных пути
подключения вместо одного.

### `Bootstrap` не персистит, каждая сцена собирает своё

Отклонено: будущие загрузчики уровней и сессия дублировали бы работу
на каждом входе в игру.

## Revisit when

- Появится больше трёх глобальных сервисов и словарь начнёт разрастаться —
  возможно, пора вводить явный `GameServices` агрегат вместо реестра.
- Появится late join или несколько сцен, живущих одновременно —
  тогда `Single` перестанет подходить и потребуется аддитивная модель.
