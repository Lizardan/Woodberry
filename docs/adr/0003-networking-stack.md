# ADR 0003 — Networking Stack

## Status

**Proposed**

## Date

2026-09-30

## Блокирует

**Stage 03 — Coop Baseline.** Нет принятого ADR → нет кода.

## Context

Игра — кооперативная. Это **архитектурное ограничение, а не фича в конце**: сетевой
слой влияет на дизайн данных, на структуру слоёв, на UI, на тестируемость. Выбрать стек
после того, как написано полгода геймплея, — значит переписать половину.

### Требования из игрового дизайна

| Требование | Следствие |
|---|---|
| Вид сверху, читаемая камера | Мало объектов, но важна плавность — нужна интерполяция |
| Кооператив, игроки равны | Нет host-привилегий, всё реплицируется |
| 2–4 игрока | Не нужна распределённая симуляция на сотни сущностей |
| Тёмная сцена, статичная геометрия | Уровень статичен, динамики немного — экономия на репликации |
| Ограниченный бюджет (`performance-budget.md`) | 60 FPS на средней машине, bandwidth < 30 KB/s |
| Хоррор, малые тики допустимы | Тикрейт 20–30 Hz вместо 60 |
| Нет опыта с конкретным стеком в команде | Простота обучения важна |

### Что уже зафиксировано в specs

- Клиент **никогда** не source of truth (`coop-networking.md`)
- Локальный и удалённый игрок — **один и тот же класс** `PlayerController`
- Спавн сущностей — **только** на authority
- Транспорт изолирован в `Assets/Scripts/Net/`, геймплей знает только `INetworkService`

## Options

### Option A — Netcode for GameObjects (NGO)

Unity-официальный, зрелый, object-oriented, хорошо документирован.

| | |
|---|---|
| Плюсы | Официальная поддержка Unity; `NetworkBehaviour` близок к привычному `MonoBehaviour`; большой корпус примеров; `NetworkVariable` с серверной валидацией из коробки; встроенные `NetworkTransform`, `NetworkObject` |
| Минусы | Тяжеловее для 2–4 игроков со статичным уровнем; `NetworkBehaviour` протекает в MonoBehaviour-наследников (нужен `Awake`-guard: не инициализировать локальное состояние на клиенте); привязка к `NetworkManager` в сцене |
| Риск | `NetworkBehaviour`-наследование в геймплее → утечка сетевого слоя в `Gameplay/`. Лечится seam-абстракцией, но требует дисциплины |

### Option B — Netcode for Entities (NetCode)

Data-oriented, ECS-based. Быстрый при большом числе сущностей.

| | |
|---|---|
| Плюсы | Производительность при тысячах сущностей; современный подход Unity; тонкий контроль над репликацией |
| Минусы | **Требует перехода на Entities/ECS** — это переписывание всего игрового кода; высокий порог входа; MonoBehaviour-слои (UI, камера) придётся строить иначе; сложнее отлаживать; заметно больше кода инфраструктуры |
| Риск | Критический: несоразмерно задаче. Проект пустой, но задача — top-down хоррор на 2–4 игрока, а не MMO |

### Option C — Mirror (сторонний)

Популярный open-source.

| | |
|---|---|
| Плюсы | Простой, понятный API, много туториалов |
| Минусы | **Сторонний**, не в официальной поддержке Unity; жизнеспособность зависит от мейнтейнеров; нет гарантий совместимости с версиями Unity; наша версия Unity — `6000.6.3f1` (свежая), совместимость не проверена |
| Риск | Технологический: в свежей версии Unity может не завестись или будет отставать |

### Option D — Photon / Mirror-подобные SaaS

Готовый хостинг, но:
- Внешний сервис = зависимость от чужого API и тарифов
- Секреты в проекте
- Для 2–4 игроков — оверинжиниринг
- Нарушает принцип «никаких секретов в репозитории»

### Option E — Отложить сеть

Начать геймплей без сети, добавить позже.

| | |
|---|---|
| Плюсы | Быстрее первые видимые результаты |
| Минусы | **Нарушает фундаментальное правило проекта.** Архитектура, спроектированная без сети, потом потребует переделки. Все `Gameplay`-модули придётся переписывать, потому что в них не будет seam'а. Это худший вариант: работа, которая придётся выбросить |
| Митигация | Сейчас: правило «все gameplay-модули принимают `INetworkService`» введено с первого дня, даже если реализация — заглушка |

## Decision

**Предлагается Option A — Netcode for GameObjects (NGO), версия подбирается при установке.**

Обоснование: задача — top-down кооператив на 2–4 игрока со статичным уровнем.
ECS здесь не нужен, а сложность NetCode for Entities не окупается. NGO даёт
достаточную производительность при минимальном пороге входа, официальную поддержку
и совместимость с нашей версией Unity.

**Решение не принято. Требуется разрешение конкретной версии пакета для Unity `6000.6.3f1`.**

## Consequences (если Option A принят)

### Positive

- Официальный пакет, совместимость с версией Unity
- Низкий порог входа, большой корпус примеров
- Достаточная производительность для 2–4 игроков

### Negative

- `NetworkBehaviour` — наследник `MonoBehaviour`, есть риск протечки в `Gameplay`
- Тяжелее, чем нужно, для нашего масштаба
- `NetworkManager` требует присутствия в сцене — нужно проектировать, как он туда попадает

### Требуемые митигации

1. **Seam обязателен.** Весь сетевой код — в `Assets/Scripts/Net/`. `INetworkService` в `Core`.
   Проверяется grep'ом (см. Stage 03 acceptance criteria).
2. **`NetworkBehaviour` не наследуется в `Gameplay/`.** Только в `Net/`. Игровые компоненты
   остаются чистыми `MonoBehaviour` и получают реплицированное состояние через сервис.
3. **Один класс на local и remote.** Не заводить `NetworkPlayerController` рядом с `PlayerController`.
   Разница — только источник ввода.
4. **Версия пакета фиксируется** в `AGENTS.md → Project facts` и в `Packages/manifest.json`.

## Alternatives to revisit

- **Option B** — если требования вырастут до десятков игроков или сотен динамических сущностей
- **Option C** — если NGO окажется непригодным для `6000.6.3f1` (проверить при установке)

## Revisit when

- Проверка установки пакета на `6000.6.3f1` провалится
- Требования вырастут до > 4 игроков
- Появятся десятки реплицируемых сущностей одновременно
