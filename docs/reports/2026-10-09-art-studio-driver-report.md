# Отчёт — драйвер арт-студии и подключение генерации

Дата: 2026-10-09. База: `main`, HEAD `12cb6b6` + шаги 0–2.
Этап: шаг 3 плана «Арт-студия внутри Unity».

## Objective

Замкнуть цикл генерации: из окна `Woodberry → Art Studio` реально создаётся
кадр, доводится до `ArtStudio/review/` и его видно кандидатом. Для этого нужен
драйвер `artgen.py` (мост Unity ↔ стенд) и подключение окна к нему: команды,
чтение событий, кнопки, список кандидатов.

Критерий шага (из отчёта шага 2): «из окна реально создаётся кадр, доводится
до `review/`, и его видно кандидатом».

## Что было найдено при реконструкции

Файл плана в репозиторий не попал (он жил в прерванной сессии OpenCode).
План восстановлен из трёх отчётов и замороженной спеки
`docs/specs/art-generation.md`: шаг 0 — норматив импорта, шаг 1 — уборка и
рабочая папка, шаг 2 — логика и окно, шаг 3 — драйвер и генерация,
шаг 4 — перегенерация по браку, шаг 5 — оверлей новых пулов.

Драйвера в репозитории не было вообще (`ArtStudio/driver/` пуста), то есть
шаг 3 начинался с нуля, а не «с середины».

## Implemented

### Драйвер `.workbuddy-ai/tools/artstudio/artgen.py` (протокол v1)

| Возможность | Как сделано |
|---|---|
| Чтение команд | `commands.jsonl` по смещению, только целые строки |
| Запись событий | `events.jsonl`, `seq` с 1 в каждом прогоне, `write` + `flush` на строку |
| Идемпотентность | `nonce`: повтор команды не применяется дважды |
| Идентификация | `driver.json` — pid драйвера, pid ComfyUI, версия протокола |
| `ping` / `stop` | `ready` с версией; вежливое завершение |
| `server_start` / `server_stop` | переиспользование живого ComfyUI, подъём, гашение (`taskkill /T`) |
| `catalog` | импорт `roster.py` стенда; пулы + список **свободных** id |
| `generate` | `shoot.py --only`, прогресс парсится из stdout, проверка стандарта, кандидат в `review/` |
| `approve` | перенос кандидата в проект по `copy_dialogue_art.destination()` |
| Отказы | неизвестная команда / нет свободных кадров → `command_rejected` с причиной |

Свободный кадр считается по **номеру**, а не по букве: `a` → `_01`, `b` → `_02`;
свободен тот id, чей номер в папке пула ещё не занят.

### Спецификация

- `ArtEvent` получил поля `protocol` (в `ready`) и `detail` (в `catalog`) —
  без них контракт из спеки было не выполнить. Это дополнение, версия
  протокола не менялась: старые события читаются как раньше.

### Unity: логика

| Класс | Ответственность |
|---|---|
| `ArtDriverState` | переходы состояния по событию: подключён/версия, состояние сервера, очередь, кандидаты, каталог |
| `DriverPool` | пул стенда; `PrefixFor(kind, group, pool)` — правило id |
| `ReviewCandidate` | кандидат из `review/` |
| `ArtCommandStore` | дописывает команду одной строкой и сбрасывает на диск |
| `ArtDriverClient` | файлы + процесс драйвера; поиск версионированного пути |

### Unity: окно

- Кнопки `Драйвер: поднять`, `Сервер: …`, `Сгенерировать` (+ поле «кадров»).
- Список `Кандидаты на ревью` с превью из файла и кнопкой `В проект`.
- Строка проблем: нет драйвера / не отвечает / расхождение версии / причина отказа.
- Драйвер поднимается при открытии окна; события дочитываются планировщиком
  окна (150 мс), как и превью.
- Убран мёртвый параметр `CatalogGroup` у `SelectPool` (был в known issues шага 2).

### Тесты

событиям, разбор каталога, замена кандидата по тому же пути, флаг обновления
ассетов, формат строки команды.

Первая версия драйвера писала вывод в свой каталог через `--out`. Оказалось,
что при вырезании фона `shoot.py` зовёт `seg.py` пакетно по ВСЕЙ папке `raw`

готовый файл из `out` стенда; кандидат теперь копируется, а не переносится.

## Known issues

- **Ростер стенда разложен целиком.** 122 id ростера уже есть в проекте,
  свободных кадров **ноль** во всех пулах. Значит кнопка «Сгенерировать» для
  существующих пулов сейчас законно отвечает отказом, и генерацию нельзя
  показать без освобождения номера. Это не поломка инструмента, а следствие
  того, что первый массовый прогон закрыл весь ростер. Расширяется шагом 5
  (`extra_pools.json` — новые пулы) или новой буквой в ростере.
- **Драйвер поднимается при открытии окна.** Процесс создаёт редактор; при
  неожиданном поведении смотреть `ArtStudio/logs/driver.log`.
- **Автозапуск не имеет выключателя.** Если это мешает, нужен флаг в
  `config.json`.
- `review/thumbs/` драйвер не заполняет: превью кандидатов окно читает из
  самого файла.

## Tech debt

- `regen_marked` и цикл «брак → перегенерация» — шаг 4.
- `extra_pools.json` не читается стендом — шаг 5.
- Проверка стандарта в драйвере импортирует `copy_dialogue_art` из
  `.workbuddy-ai/tools/` и подменяет у него корень проекта — правило одно,
  но связь неявная; стоит перенести `destination()` в общий модуль.

## Assumptions

- Команда `reject` драйверу не нужна: брак хранит `feedback.json`, его пишет
  Unity. Поэтому в драйвере её нет, и это осознанно, а не забыто.
- `outDir` стенда = `<standDir>/out` (совпадает с `BASE_OUT/out` в `shoot.py`,
  где `BASE_OUT` — `env PORTRAIT_OUT` или корень стенда). Если кто-то задаст
  `PORTRAIT_OUT` иначе, путь надо будет переопределить в `config.json`.
- Свет для фона берётся из `config.json` (`light`), для персонажа — свой
  (`ch['light']`), как в `scene.subject_prompt`.

## Risks

- **Окно само поднимает процесс при открытии.** Это удобно, но неожиданно
  для редактора; при проблемах смотреть `ArtStudio/logs/driver.log`.
- **Генерация недоступна при полном ростере.** Пока шаг 5 не даёт добавлять
  пулы, кнопка «Сгенерировать» на существующих пулах будет отвечать отказом —
  и это легко принять за поломку.
- **Зависимость от поведения `shoot.py`.** Драйвер рассчитывает, что готовый
  арт лежит в `out` стенда и назван `<id>_<style>.png`. Правка стенда сломает
  мост; поэтому спека фиксирует это явно.
- **`Has.Count` на `IReadOnlyList` падает в NUnit** — учтено в тестах, но
  грабли повторятся в новых тестах, если о них не знать.

## Manual QA steps

1. Открыть `Woodberry → Art Studio`. Ожидаемо: кнопка станет
   «Драйвер: подключён», в строке внизу пропадёт «драйвер не отвечает».
2. Выбрать пул в дереве. Ожидаемо: в панели справа «пул: … свободно: N/M».
3. Если N = 0 — нажать «Сгенерировать» и убедиться, что в строке проблем
   появилось «в пуле … нет свободных кадров» (это верный ответ, не баг).
4. Чтобы получить свободный кадр: временно убрать любой кадр пула из
   `Assets/…/Dialogue/…` (например, в `ArtStudio/review/replaced/`), нажать
   «Обновить», затем «Сгенерировать».
5. Дождаться кандидата: он появится в списке «Кандидаты на ревью» с превью
   и покрытием. Нажать «В проект» — кадр встанет в `Assets`, дерево обновится.
6. Вернуть исходный кадр из `replaced/`, если это была проверка.

## Дополнение (2026-10-09): пропорции превью и ресайз правого блока

Запрос: кадр превью всегда в пропорциях портрета (480×720), растёт и вбок,
а не только вверх; правый блок целиком расширяется/сужается вместе с окном,
а не одна рамка кадра.

### Как сделано

- `.panel-right` вместо фиксированных `430px` получил `width: 32%`:
  ширина блока считается от окна, поэтому «шире/уже» — это сам блок
  (заголовок, подписи, поля, кнопки), а не только рамка кадра.
- Пропорция кадра не задана числом. `FitPreview()` берёт её у самого
  изображения (`texture.width/height`) и считает наибольший прямоугольник
  этой пропорции, влезающий в `previewHolder`; `GeometryChangedEvent`
  на holder'е пересчитывает размер при каждом ресайзе. Так портрет (2:3) и
  фон (856×480) держат каждый свою пропорцию.
- Рамка кадра в USS больше не тянется: `width`/`height` ставит окно,
  `-unity-image-sizing: scale-to-fit` оставлен как страховка от растяжения.

### Измерено в запущенном редакторе

| Окно | Правый блок | Доля от окна | Превью | Пропорция |
|---|---|---|---|---|
| 1920×983 | 614 | **0,320** | 396×595 | **0,666** (2:3) |
| 1675×1094 | 536 | **0,320** | 470×706 | **0,666** (2:3) |
| 900×820 | 380 (упёрся в `min-width`) | 0,422 | 288×432 | **0,667** (2:3) |
| 700×700 | 380 (упёрся в `min-width`) | 0,543 | 208×312 | **0,667** (2:3) |

Доля блока от окна одинакова на широких размерах (0,320) — блок следует за
окном; пропорция кадра неизменна (0,666) на всех четырёх размерах — без
растяжения. Замер снят `execute_code` из `rootVisualElement` окна.

Порог `min-width` тоже измерен: при 900 px блок ровно 380 и ниже не идёт, доля
растёт до 0,422, потому что блок перестаёт следовать за окном и держит минимум.
Ниже ~800 px по окну не влезают три колонки: при 700 px замерено
`left=180`, `center=240`, `right=380` (сумма 800) — колонки стоят на своих
`min-width` и выходят за окно. Это свойство трёхколоночной раскладки, а не
следствие правки: `min-width: 380px` у правого блока был и раньше, пороги
не поднимались.

### Не проверено

- Ручной drag рамки окна мышью: размер задавался кодом, а не перетаскиванием.
- Перенос строк в подписях при 380 px глазами не смотрел: замерены размеры
  элементов (кнопка «Сгенерировать» — 104×22, высота не менялась), но
  перенос текста в `framePath` приборно не измерялся.

## Дополнение 2 (2026-10-09): драйвер переигрывал историю команд и «врал» о подключении

Найдено живой инспекцией окна после перезапуска сессии: окно показывало
«Драйвер: подключён» при мёртвом драйвере, а в строке проблем висело
«драйвер: кандидат не найден: …», хотя ревью пусто.

### Дефект 1: флаг подключения не гаснет

`DriverConnected` ставится событием `ready` и нигде не сбрасывается: о смерти
процесса события не приходит. Последствия: окно рапортует «подключён», строка
проблем молчит, а кнопка «Сгенерировать» остаётся активной и пишет команду в
файл, который никто не читает — отказ выглядит как исправный инструмент.

### Дефект 2 (важнее): драйвер переигрывал все команды за прошлые сессии

`CommandTail` начинал читать `commands.jsonl` с нулевого смещения, а файл не
обнуляется. В нём лежало 45 команд (21 `ping`, 21 `catalog`, `generate`,
`approve`, `stop`). Новый драйвер исполнял их заново:

- 21 `ping` → 21 событие `ready` и 21 `catalog` в файле событий;
- старый `stop` → **драйвер гас через ~2 с после каждого старта**
  (в логе 02:00:49/52, 02:01:01/04, 02:01:13/15, 02:02:19/21);
- старый `approve` → `command_rejected` «кандидат не найден» (тот самый
  залипший текст), а `generate` запустил бы реальную генерацию на каждой
  перекомпиляции Unity — минуты GPU впустую.

`seen_nonces` живёт в памяти процесса и от истории не защищает.

### Исправления

| Файл | Что сделано |
|---|---|
| `ArtDriverState.cs` | `MarkDriverDisconnected()`: сброс подключения и версии протокола |
| `ArtDriverClient.cs` | `Poll()` сверяет флаг с живым процессом: `connected && !IsDriverAlive` → сброс |
| `ArtStudioWindow.cs` | по переходу «нет → есть» повторно просит `ping` + `catalog` |
| `artgen.py` | `CommandTail` стартует с конца последней целой строки; `--once` сохраняет пакетную семантику (`replay_history`) |

Зачем повторный запрос каталога: команды, отправленные в момент спавна
процесса, чаще всего оказываются левее смещения старта, и без повтора панель
пула навсегда осталась бы с «нет данных стенда».

### Проверено живьём

| Что | До правки | После |
|---|---|---|
| Драйвер после старта | гас через ~2 с (переигранный `stop`) | жив, pid 38140, в логе нет «остановлен» |
| `events.jsonl` после старта | 68 событий, из них 21 `ready`, 2 `command_rejected` | **5 событий**: `ready`, `server_state`, `ready`, `log`, `catalog` |
| Панель после старта | «подключён» при мёртвом драйвере | «Драйвер: подключён», каталог **81 пул**, строка проблем пуста |

## Дополнение 3 (2026-10-09): ширина правого блока равна ширине кадра

Запрос: окно можно растянуть так, что кадр уже правого блока; ширина блока
должна подстраиваться под кадр, а не под окно.

### Как сделано (вторая версия; первая оказалась петлёй)

- Ширину блока и размер кадра считает **одна чистая функция**
  `PreviewFit.Compute()` (`Assets/Scripts/Editor/ArtStudio/PreviewFit.cs`):
  оба числа выводятся из одной ширины кадра, поэтому разойтись не могут.
- **Первая попытка была неверной.** Блок и кадр считались двумя проходами
  (`FitRightPanel()` → `FitPreview()`), причём ширина блока выводилась из
  ширины места под кадр — а это место задаёт сам блок. Задача замкнулась:
  блок «залипал» на той ширине, с которой начал (в живом окне — 380 px из
  USS), и на растущем по высоте окне оставался узким, а кадр в нём —
  маленьким. Отсюда же и полоса между блоком и кадром: два расчёта по
  раскладке прошлого кадра плюс `floor` по обеим осям.
- Правило: **блок равен кадру плюс свои отступы, ровно, без запаса**
  (`RightPanelChrome = 13` = 6+6 падинга плюс рамка блока; прежний запас +2
  убран). Ширину кадра задаёт высота (`высота × пропорция`).
- Входы функции не зависят от её результата: высота места под кадр и ширина,
  которую окно реально может отдать блоку (окно − левая колонка − минимум
  центральной). Второе не даёт высокому узкому окну выдавить центральную
  колонку. Ноль вместо ширины означает «неизвестно» — тогда блок считает
  только высота.
- Пропорция берётся у выбранного кадра (`SourceSize()`): у портрета 2:3,
  у фона 856×480 — поэтому блок следует за кадром, а не за средним.
- Пол 160 px и потолок 760 px пересчитаны в пол и потолок **кадра**, значит
  кадр заполняет блок и в упорах. Исключение одно: место ниже пола по
  высоте — кадр упирается в высоту; в студии недостижимо, потому что
  `.preview-holder` держит `min-height: 220px`.
- Пересчёт висит и на месте под кадром, и на самом окне
  (`OnWindowResized`): высоту окна первым замечает только окно.
- Повторная запись того же числа не делается: окно сравнивает с тем, что
  выставило само (`_appliedPanelWidth`), а не с `resolvedStyle` — та честно
  отстаёт на кадр.
- Масштаб картинок перенесён в C# (`Image.scaleMode`): USS-свойства
  `-unity-image-sizing` в этой версии Unity нет — оно молча игнорировалось,
  а планировщик USS писал три warning'а. Там же исправлены
  `-unity-text-align: left` → `middle-left` и `-unity-text-overflow-position:
  ellipsis` → `end`. Миниатюры теперь заполняют свой квадрат, как и было
  задумано в комментариях, а не вписываются в него.

### Измерено в запущенном редакторе

## Дополнение 5 (2026-10-09): шаг 4 — перегенерация брака

Запрос: довести цикл брака до конца — пометил кадр браком, нажал
«Перегенерировать», получил нового кандидата.

### Как сделано

| Файл | Что сделано |
|---|---|
| `artgen.py` | `cmd_regen_marked`: читает `feedback.json`, переводит пути в id стенда, кладёт кадры в ту же генерацию, что и `generate` |
| `ArtDriverClient.cs` | `RegenerateMarked()` — команда без полей |
| `ArtStudioWindow.cs` | кнопка «Перегенерировать брак (N)»: N считает журнал ревью, кнопка молчит при нуле и без драйвера |
| `ArtStudio.uxml` | сама кнопка в правом блоке |
| `docs/specs/art-generation.md` | таблица команд + правила перегенерации по браку |

Список кадров окно не присылает: марки — это пути, а какие id за ними стоят,
знает драйвер (у него каталог стенда). Кадр в проекте получает **следующий
свободный номер** пула, кандидат в `review/` — **тот же id** ("попробовать ещё
раз"). Пропуски (кадр вне ростера, нет свободного номера) уходят событием
`error`, а не молчанием; если брака нет вовсе — честный `command_rejected`.

### Найденный и исправленный дефект: перегенерация возвращала тот же кадр

Первый же живой прогон показал главное: новый кандидат оказался **побайтово
идентичен** старому (`md5 50425154…`, 466 588 байт). Причина — не в
перегенерации как таковой, а в том, что драйвер не передавал стенду сдвиг
сида: у `shoot.py` есть `--seed-shift`, а `generate_frames()` его не слал, и
тот же id получал тот же сид. Без этого «перегенерировать» — кнопка, которая
тратит две минуты GPU и возвращает ту же картинку.

Исправление: драйвер выбирает сдвиг на прогон, передаёт `--seed-shift` и
пишет число в лог (по нему прогон повторяется). Второй прогон — другой кадр
(`md5 a2db35b4…`, 458 071 байт). Это ровно тот случай, когда проверка обязана
сравнивать файлы, а не смотреть на события.

| Что | Результат |

| Кнопка при одном браке | «Перегенерировать брак (1)», активна; после снятия брака — «Перегенерировать брак», неактивна |

| Разбор решений | проверен на реальном каталоге: кандидат → тот же id; кадр проекта со свободным номером → следующий номер; кадр вне ростера и пул без номеров → пропуски; три одинаковых марки → один кадр |
