# Арт-студия — прогресс по этапам и три полосы

**Дата:** 2026-10-10
**Инкремент:** 1 из 2 (прогресс). Второй инкремент — вкладки и промпты.
**Статус:** реализовано, EditMode 280/280 Passed, живой прогон **не проверен** (см. «Верификация»).

---

## Что было не так

Жалоба была сформулирована как «полоса прогресса стоит и заполняется один раз».
Разобрался не по ощущениям, а по коду — и причина оказалась не в интерфейсе.

### Симптом

На заказе из 5 кадров (`p_Craftsmen_Potter`, замер 2026-10-10 15:20, 154 с):

- нижняя полоса («Текущий кадр») заполнилась один раз — на первом кадре — и дальше
  стояла на 100 %;
- верхняя полоса («Вся заявка») продолжала ползти вперёд.

### Причина: цепочка из трёх звеньев

1. **`artgen.py`, `generate_frames`** — `item_done` для кадров уходит в цикле
   `for stand_id in ids: accept_candidate(...)`, который стоит **после**
   `proc.wait()`. То есть пока стенд рисует кадры №2..№5, задание №1 в очереди
   навсегда остаётся `Running`.
2. **`ArtDriverState`, обработка `item_progress`** — новое задание становилось
   `Running` только при `Jobs.Running == null`. Поскольку кадр №1 не закрыт,
   кадры №2..№5 `Running` не становились **никогда**.
3. **`GenerationProgress.FramePercent`** — «текущим» был первый не закрытый
   кадр с `Percent = 99`, а постобработка доводила его до 100 % за
   `PostSeconds = 4.0`. Полоса уезжала на 100 % и оставалась там навсегда.

Общая полоса при этом ползла честно: `Overall` для не-текущих заданий брала
`job.Percent`, а `SetProgress` пишет по `ev.id` — то есть проценты сэмплера
кадра №2 попадали прямо в сумму. Отсюда ровно то наблюдение, что описано:
верхняя живая, нижняя застывшая.

### Отдельно: почему прогресс «останавливался»

Долгие места, где событий не было вовсе:

| Место | Замер | Почему молчало |
|---|---|---|
| Прогрев моделей | 32–42 с | стенд печатает `--- ПРОГРЕВ`, дальше тишина |
| Загрузка весов на холодном сервере | до 30 с | событий нет по построению |
| **Пакетная вырезка фона** | десятки секунд | `shoot.py` вызывал `seg.py` через `subprocess.run(capture_output=True)`: построчный прогресс `[i/N] файл` копился в буфер и выводился **только после конца вырезки всей папки raw** |
| Проверка кадров | 52 с | 118 строк покрытия печатались одним куском |

Плюс `PostSeconds = 4.0` — полоса доезжала до 100 % за четыре секунды и
держалась там минутами, пока шла настоящая работа.

## Что сделано

### Стенд (`F:\ai\portraits\shoot.py`)

- `mark()` и `mark_frame()` — построчные маркеры этапов в stdout прогона,
  договорённый формат `@@stage <этап> <сделано> <всего> [пояснение]`
  и `@@frame <id> drawn`.
- `cut_characters` переведён с `subprocess.run(capture_output=True)` на
  `Popen` с построчным чтением: строки `seg.py` уходят наружу **по мере
  появления**, а не разом в конце. `stderr` присоединён к `stdout` намеренно —
  отдельный канал при построчном чтении без присмотра даёт дедлок.
- Маркеры `cut`/`check` по ходу вырезки и проверки, `@@frame` — сразу после
  успешной отрисовки каждого кадра.

### Драйвер (`artgen.py`)

- Разбор маркеров `STAGE_LINE` / `FRAME_DONE_LINE` → события `item_stage`
  и `item_drawn`.
- `item_progress` получил поле `stage` (`warmup` / `prepare` / `sample`).
- Этап `copy` шлётся вокруг проверки и копирования каждого кадра.
- **Убран выдуманный `percent=3` для ожидающих кадров.** Он был нужен, чтобы
  полоса не стояла в нуле, но враньём он же: кадр, к которому стенд ещё не
  приступил, показывал ~17 % готовности, и общая полоса стартовала не с нуля.

### Unity

- `ArtEvent` — события `item_drawn`, `item_stage`, поля `stage`, `done`, `total`.
- `GenerationJob` — `Drawn`, `Stage`.
- `JobQueue.Activate(job)` — задание становится текущим **по своему
  stand-id**, снимает `Running` с остальных и честно сбрасывает проценты,
  время и признак отрисовки. `SetProgress` теперь принимает `stage`.
- `JobQueue.MarkDrawn(id)` — «кадр отрисован, ждёт приёмки».
- `GenerationProgress` переписан: `Overall` / `Share` / `FramePercent` /
  `StagePercent` / `StageTitle` / `StandStageText`. Все — чистые функции.
- Окно: третья полоса `stageBar`, список кадров заявки со статусами,
  человеческие подписи фаз вместо «подготовка: событий нет 0:12».

### Три шкалы

| Полоса | Источник | Поведение |
|---|---|---|
| Вся заявка | среднее вкладов: принят 100, отрисован 90, рисуется по кадровой шкале, ждёт 0 | не стартует с ненулевого, различает «нарисовано» и «принято» |
| Текущий кадр | `prepare` 0..15 по времени, `sample` 15..100 по шагам | **сбрасывается в ноль на каждом кадре** |
| Текущий этап | счётчик `37 из 118` точно; без счётчика — по времени с потолком 90 % | не показывает «готово» там, где ничего не сделано |

Ключевое: `DrawnWeight = 90`. Кадровая полоса значит «отрисован», а не
«в проекте» — приёмка идёт за пределами этой шкалы и видна в полосе этапов.

## Тесты

`Assets/Tests/EditMode/`:

- `ArtDriverStateTests.FourFrames_FrameBarPassesFromZeroToHundredOncePerFrame` —
  регрессия на главный баг: четыре кадра, четыре прохода 0→100, текущим
  каждый раз становится именно тот кадр, за которым идёт стенд.
- `ArtDriverStateTests.Progress_WhenNextFrameStarts_DoesNotInheritPreviousPercent` —
  новый кадр начинается с нуля, общая полоса не почти полная.
- `ArtDriverStateTests.ItemStage_KeepsCounterAndSurvivesIntoWindow`,
  `ResetStandStage_ClearsLeftoverFromPreviousRun`.
- `GenerationProgressTests`: вклад отрисованного кадра, счётчик этапа,
  потолок этапа без счётчика, монотонность, усреднение по заявке, ноль на
  ожидающих кадрах.

четыре раза на живой генерации» — это `Not verified` до прогона.
