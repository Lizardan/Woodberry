# Spec — Coop Networking

Статус: Draft
Зависит от: `../adr/0003-networking-stack.md`

**Это архитектурный документ. Читай до того, как писать любой геймплейный код, который
должен работать в кооперативе. Не реализуй сетевую логику до того, как эта спека согласована.**

## Модель

Игра — **co-op без выделенного сервера и без host-привилегий**. Все игроки равноправны.
Выбранный транспорт решает, кто является authority, — но геймплейный код об этом не знает.

## Фундаментальное правило

> Клиент **никогда** не является source of truth для игрового состояния.

Клиент отправляет **намерение**. Авторитет решает и **результирует**.

```
Игрок нажал «взять фонарь»
  → клиент шлёт intent: PickUpRequest(itemId)
  → авторитет проверяет: существует ли, свободен ли, в радиусе ли, не занято ли
  → авторитет применяет: инвентарь += фонарь, item помечается claimed
  → авторитет реплицирует результат: InventoryChanged, ItemClaimed
  → все клиенты, включая инициатора, применяют результат локально
```

## Что авторитетно, а что нет

| Состояние | Авторитет | Репликация |
|---|---|---|
| Позиция и поворот игрока | Хост/сервер | Да, с интерполяцией |
| Здоровье, ресурсы, инвентарь | Хост/сервер | Да, по событию изменения |
| Состояние предметов в мире | Хост/сервер | Да, по событию |
| Поведение ИИ / ИИ врагов | Хост/сервер | Результаты, не внутренние стейты |
| Направление камеры | Локально клиента | Нет |
| Звук, VFX, анимация | Локально клиента | Нет |
| UI, HUD | Локально клиента | Нет |

**Правило:** реплицируй состояние и результаты. Не реплицируй то, что клиент может
восстановить локально (анимации, эффекты, UI, косметику).

## Модель владения

Играется на одном инстансе сети: local + remote игроки в одной сессии.

- **Local player** — читает локальный ввод через `IInputReader`, отправляет intent.
- **Remote player** — получает реплицированное состояние, интерполирует визуал.
- Оба используют **один и тот же** `PlayerController`. Разница только в источнике ввода.

Это ключевое требование: если локальный и удалённый игрок — разные классы, сеть
расползётся по коду и станет неразрешимой.

## Спавн

Спавн — **только** на стороне authority. Клиент никогда не создаёт игровые сущности сам.
Клиентские сущности — это префабы с визуалом и локальной анимацией.

## Join / Leave

- Join: клиент получает полный снапшот мира (для host) или инкрементальный (для клиента).
  Полный снапшот обязан содержать позиции всех сущностей, иначе новичок спавнится в пустоте.
- Leave: authority удаляет сущность, реплицирует удаление.
- Локальный disconnect не должен ронять authority.

## Частота и интерполяция

Значения ниже — стартовые и требуют профилирования. Зафиксированы здесь, чтобы
изменение было осознанным, а не случайным.

| Параметр | Стартовое значение |
|---|---|
| Частота симуляции | 20–30 Hz |
| Частота репликации позиции | 10–15 Hz |
| Интерполяция на клиенте | Да, с буфером ~100 ms |
| Снапшот при join | Полный |
| Предсказание движения | Только local player, с серверной коррекцией |

## Транспортный seam

Геймплейный код **не знает**, работает ли он в сети.

```
Gameplay  →  INetworkService (интерфейс в Core)
                ↑ реализация
             Net/  (единственное место с сетевым кодом)
```

В геймплее **не должно быть** строк вида `if (isNetworked)`. Если нужно проверить
«я сейчас authority» — это запрос к `INetworkService.IsAuthority`, а не к транспорту.

## Ошибки, которых избегаем

- Клиентские запросы без серверной валидации (читерство, рассинхрон)
- Репликация `Transform` целиком каждый кадр для всех объектов
- Отсутствие интерполяции → дёрганое управление на 20 Hz
- Спавн сущностей на клиенте
- `NetworkVariable` на компоненте, который есть и на клиенте, и на сервере, но в разном состоянии
- Отписка от сетевых событий не в паре с подпиской (утечки, краши)
